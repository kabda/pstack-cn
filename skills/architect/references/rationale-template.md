# 设计理由模板

随类型草图交付的说明文字，限一页。标题使用句首大写风格，不写套话。用实际内容替换斜体注释。

<a id="problem"></a>

## 问题

*一个段落。说明要做什么，以及现有系统或约束的哪些特点使结构选择并不显然。如果[阶段 A](../SKILL.md#phase-a-ground-the-problem)发现了设计必须遵守的约束（需要互操作的现有类型、不能破坏的调用者、跨越边界的不变量），在此列明，让读者看到与你相同的约束。*

<a id="usage-callers-view"></a>

## 使用方式（调用者视角）

*先写这一部分，再写类型草图。展示使用者会阅读的 README 或快速入门，以及他们自己代码中两三个真实的调用位置：导入什么、调用什么、返回什么。[结构](#shape)中的类型草图由此推导，两者必须一致。发生分歧时，让草图适应使用方式，而不是反过来。调用者体验就是规格，类型为其服务。*

<a id="shape"></a>

## 结构

*推荐的架构。先讲数据结构，再讲数据如何流经签名。点明承载整体设计的关键决策。说明哪些不变量编码在类型中、验证位于何处，以及系统有意不做什么。明确评价接口深度：公共接口隐藏了哪些复杂性，仍向调用者暴露什么，为什么接口规模恰好够用。引用每项决策背后的原则（例如 `per boundary-discipline`），不要重述原则。*

<a id="synthesis-decision"></a>

## 综合决策

*由 [arena](../../arena/SKILL.md) 填写。记录以哪个候选方案为基础及原因，从其他各方案借鉴什么，以及拒绝了什么、为什么。*

<a id="tradeoffs-accepted"></a>

## 接受的取舍

*每个所选结构的取舍各列一项。形式为“我们接受 X，以换取 Y”。指出未来读者可能误以为是疏漏的所有内容，包括看似过早优化或过早简化的部分。*

<a id="alternatives-considered"></a>

## 考虑过的替代方案

*必填。至少列出一种具体替代结构，用一行说明为何落选。评价每种替代方案时看接口深度，不能只看实现是否简单。指出它向调用者暴露和隐藏的复杂性。如果设计空间中确实有竞争方案，这里应列两三个；若约束迫使答案唯一，列一个也可以，但结论应表述为“这是唯一可行的结构，因为……”。避免列出同一结构的不同变体。本节记录所选结构在设计过程中考虑并否决的替代方案，不是其他执行者的候选方案。*

<a id="open-questions-and-risks"></a>

## 待解问题与风险

*勾勒草图时注意到、需要人权衡的事项，以及实现开始前值得指出的风险。用问题而不是断言表达，让人的回答能解决问题，而不只是成为一条评论。*

<a id="next-implementation-step"></a>

## 下一实现步骤

*根据草图首先构建什么，用一句话说明。即综合之后（或按需设置检查点时，在阶段 D 批准之后）立刻开始编写的内容。*
