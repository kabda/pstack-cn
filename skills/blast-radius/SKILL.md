<a id="blast-radius"></a>

# 影响范围

在交付前找出改动会破坏哪些其他地方。用于“blast radius of X”、“what could this break”，或审查你尚不信任的小型 diff。

与 `how`、`why` 配套。`how` 说明代码做什么；`why` 说明它为什么这样设计；blast-radius 说明它会破坏其他哪些地方。

任务不是列出调用者。智能体一秒钟就能搜索到它们。任务是找出搜索无法显示的破坏。

<a id="dont-trust-your-own-writeup"></a>

## 不要相信自己写的分析

一份听起来正确的影响范围分析毫无价值。无论真伪，它都可能很有说服力。因此不要只交回分析文档。找出整个判断依赖的一两个事实，用运行代码证明它们。

<a id="how-sure-are-you"></a>

### 你有多确定

对于改动安全性所依赖的每个事实，在成本合理的范围内尽量推进到下面列表更靠后的位置，并说明停在哪一级。

1. 你这样说。单独而言毫无价值。
2. 你指出了代码行。是真实的 `file:line`，或库自身的源码。
3. 你说明坏情况不可能发生。逐步推演故障路径，证明无法到达。
4. 你实际运行过。脚本或测试调用真实代码，判断错误时会明确失败。
5. 你在运行中的应用里复现过。

第 4 级通常只需要一个小脚本：导入应用实际发布的同一库，调用你担心的那个精确函数。

<a id="steps"></a>

## 步骤

1. 阅读改动。查看 diff，新增、修改和删除的符号，以及现在行为的变化，包括 diff 没有明说的部分。使用 `why` 的第 2 步获取 PR 和提交。
2. 找出使它安全的关键事实。大多数看似有风险的改动，之所以安全，是因为一个事实，例如“此调用只丢弃已经失效的缓存项，没有其他作用”。找出这个事实。若成立，多数风险情况就能一起排除。把时间花在这里，而不是列一长串可能性。
3. 查看搜索的边界之外。阅读所调用库的源码，检查其锁定版本及本地补丁。弄清执行时机：微任务、卸载与清理、Solid 与 React 的差别。追踪符号搜索会漏掉的关系：API 返回的 JSON、数据库列、线协议格式、另一种语言读取相同字节、功能开关，或下游三跳之外的代码。
4. 如实评估每项风险。给出真实发生概率和发生后的实际代价。保留已确认的风险，把检查后排除的风险另列。遵循与 `why` 相同的规则。引用真实的 `file:line`；搜索无结果也是有效答案；绝不能编造调用者或 API。
5. 证明关键事实。编写运行真实代码的脚本或测试，执行它，并粘贴实际结果。
6. 对于大型或范围广的改动，以 `arena` 方式运行。向多个模型提出相同问题并合并答案。不同模型会捕获不同的真实缺陷。

<a id="what-to-hand-back"></a>

## 交付内容

- **它做什么。** 说明变化，包括不明显的部分。
- **使它安全的关键事实。** 陈述事实，说明证据达到哪一级，并展示证明。如果无法证明，标记为未证实。
- **风险。** 每项说明破坏方式、`file:line`、概率与严重程度，以及检查方法。重要风险贴出证明。
- **已排除。** 检查了什么，为什么没有问题。
- **合并前。** 能捕获真实缺陷、成本最低的测试或复现，包括你写的脚本。

使用 `unslop` 处理表述，引用真实代码，并在任何内容公开前移除隐私信息。

**回复：**按上述结构给出分析，关键安全事实必须已获证明，或明确标记为未证实。
