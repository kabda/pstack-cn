# 怎样写提示词

提示词陈述意图和完成检查。操作手册提供步骤，因此几句平实的话比一份规格更好。

<a id="put-in"></a>

## 应写入

- 目标。说明哪里不对，或用户想要什么。
- 完成检查。它必须能通过或失败。“做得更好”和时长都不是检查。
- 要展示的证明。要求真实命令输出、流程视频、存储值，或改动前后数值。
- 用户已知信息。症状、复现步骤、日志或链接，能省去智能体一次搜索。
- 真实约束。“先复现”“暂不改代码”“行为零变化”“继续前让我审查”，都会改变智能体行动。

<a id="leave-out"></a>

## 不应写入

- 具体做法。说明要达成什么，给智能体找到更好方式的空间。
- 技能或步骤列表。手写顺序可能丢弃或重排操作手册保留的步骤。只有要覆盖某一选择时才点名技能。
- 在智能体重述问题前，先给用户对原因的理论。说出的猜测会收窄搜索。

<a id="load-the-context-first"></a>

## 先加载上下文

- 报告杂乱时，要求智能体先用自己的话、用通俗英语重述根本问题，再做其他事情。这样误读会在写任何代码前暴露。
- 新聊天先用 `/recall` 回顾该主题的既往工作。旧聊天含有新智能体没有的上下文。
- 改不熟悉的代码前，用 `/how` 查机制、`/why` 查原因。没有追踪形成心智模型的智能体，会在第一个看似合理的位置修症状。
- 用 `/teach` 要求论证选择，例如“说服我：它修复的是原因，而非症状”。论证比摘要更容易核查。

<a id="design-before-the-plan"></a>

## 先设计，再计划

- 绝不直接采用第一个设计。要求为几个选项做原型；UI 提供截图或视频，再根据证据选择。
- 用原型回答开放问题。不要对抽象计划做对抗审查，因为审查者会发明从不发生的风险。
- 对共享包或 API，先要求 README 或教程，再反推代码。文档成为智能体自检的目标。
- 设计确定后才要计划，计划每步都以检查结束。

<a id="follow-up-short"></a>

## 后续指令保持简短

- 聊天已有任务时，“执行”“继续”“一直推进到完成”就是完整提示词。
- 换主题时以“new task”（新任务）开头；否则模式会将消息视为下一步。

<a id="before-stepping-away"></a>

## 离开之前

- 说“im going to bed”（我要睡觉了）或“im stepping away”（我要离开一会儿），让智能体停止提问。
- 把完成写成每轮可执行的检查，并把谓词交给 `/loop`。
- 要求从明确的基分支创建新 Git 工作树。
- 预先回答智能体会因此停下的问题，例如“提交前不用问我”。
- 要求记录决策日志，方便之后审计。
- 给出退出条件：“如果几小时后确实仍被阻塞，停止并写明原因。”

<a id="steer-in-one-line"></a>

## 用一行调整方向

- 重述目标：“我说目标是复现，还没要求修复。”
- 点名原则：“应用 prove it works（证明它能工作），展示真实输出，不是构建日志。”
- 原则名称能起作用，是因为智能体已经读过规则。回复会说明该规则改变了哪个决策。
