# 技术写作

写到让疲惫的工程师第一次读就能理解。应用全部四层标准。

三条规则优先于这些层次：

- **删去每个不起作用的词。** 不用某个词句子仍成立，就删掉它。"In order to" 改为 "to"（两者均表示“为了”），"It is important to note that" 直接删除。
- **用简短、日常的词。** "Use" 而非 "utilize"（使用）；"Help" 而非 "facilitate"（帮助）；"Do" 而非 "perform"（做）。长词必须以更高准确性来证明长度合理。
- **规则使句子更差时，换一种方式修，或保持原样。** 遵循所有规则却像机器写的句子，仍然失败。

代码库就是词表。使用真实符号、文件、参数或命令名，不用同义词，也不用描述来替代。

不要发明行话。使用开发者会说出口的词：“移动”“删除”“只会减少的预算”，而非“疏散”“棘轮”或“终局”。有名称的模式可以用，但文档首次出现时要解释。在回复中，提议将新发现的不良用词及其替代词加入 `unslop` 的抽象隐喻规则，并给出 diff。不要编辑该技能。

<a id="vary-the-rhythm"></a>

## 变化节奏

文档即使遵循全部层次，仍可能像机器写的：每句话都短促、没有任何观点，也没有具体内容。

- 有意识地混合长短句。短句点明观点，长句承载事实及其条件或后果。
- 一句一个意思，不代表每句一样长。承载两个意思的句子要拆，承载一个意思的长句可以保留。
- 写作模式允许时，表达观点。解释需要权衡取舍，就应说明你的判断，而非只列优缺点。参考资料则保持客观平实。
- 要具体，不要空洞。别说“schema 变化可能导致问题”，而说“列重命名会让构建失败”。

<a id="pick-the-mode-first-diátaxis"></a>

## 先选择模式（Diátaxis）

一份文档只用一种模式。用两个问题选择：内容服务于行动（做事）还是理解（思考）？服务于学习还是实际工作？

- 行动 + 学习：**教程**。
- 行动 + 工作：**操作指南**。
- 理解 + 工作：**参考资料**。
- 理解 + 学习：**解释**。

这套判断可以用于整份文档，也可以用于一句话。

**教程：边做边学。** 让学习者成功是你的责任，不是他们的责任。开头说明学习者会构建什么，而不是会“学到”什么。每步都产生可见结果，而且应尽早、经常出现。说明他们应该看到什么：预期输出、提示符变化、日志行。解释收缩为一个从句和一个链接。保持具体。用“我们”写指令：“先做 x。现在做 y。”

**操作指南：通往目标的步骤。** 解决一个人面对的问题，而非展示机器能做的一项操作。假定读者有能力，跳过教学。只讲行动：不离题、不讲背景、不为完整而完整；这些内容改用链接。允许分支与判断：“如果想要 x，就做 y。”用任务命名指南：“如何校准雷达阵列”，而非“雷达阵列校准”。

**参考资料：供查阅的事实。** 只描述，不指示、不说服、不表达意见。保持平实、完整、确定。直接陈述事实、选项、限制和错误，不加保留措辞。结构与描述对象对应，让代码和文档可以一起导航。内容放在读者预期的位置，能从代码生成就从代码生成。

**解释：理解及原因。** 限定一个主题，离开产品也能阅读。每个标题前都应能隐含加上“关于……”。围绕一个真实的“为什么”问题展开，提供设计决策、历史、约束、替代方案等背景。只有这里允许表达意见，其他模式不允许。

不要混合模式：教程里不放参考表，参考资料里不手把手教学，操作指南里不争论。拆开并互相链接。

<a id="write-sentences-to-the-reader-google-developer-style"></a>

## 面向读者写句子（Google 开发者风格）

- 用“你”称呼读者，用现在时。只有确实以后才发生的事才用将来时。
- 说明谁做什么：“编译器检查”，而非“被检查”。只有行动者未知或无关紧要时才用被动。
- 指令使用命令句：“点击提交。”事实直说。绝不写“应当被完成”。
- 条件先于指令：“要删除文档，点击删除。”
- 常见情况先讲，例外随后。
- 像一位懂行的朋友。不要流行词、比喻语言，指令里不用“请”，流程里绝不用“只需”“简单”“快速”。真简单，读者就不会来读。
- 不要预告尚未推出的能力（“我们很快将支持……”），也不要连续几句以同一短语开头。
- 链接文字说明去向：页面标题或简短描述。绝不用“点击这里”。优先在当前页给一句背景，而非直接把读者引到站外。
- 标题承载观点，不只点题（“先选择模式”，而非“模式”）。英文用句首大写。任务标题用直接的动词短语（“创建实例”），概念标题用名词短语。每页一个 h1，不跳标题层级。
- 有顺序的步骤用编号列表，其他内容用项目列表。用完整句子引出列表，列表项结构平行。
- 代码用代码字体，UI 元素用**粗体**。英文列表使用连续逗号。删去“等等”，在开头直接说明列表不完整。

<a id="make-statements-load-one-at-a-time-ste-rules"></a>

## 每次只表达一条陈述（STE 规则）

- 每句话一条指令，其他地方每句话一个意思。
- 英文指令约超过 20 词、其他句子约超过 25 词时拆分。
- 警告或条件放在其保护的步骤前：“热油接触皮肤可能造成伤害。”
- 保留英文冠词 "the" 和 "a"："Remove backup file" 有两种读法，"Remove the backup file" 只有一种。
- 每个词只承担一种含义和一种作用，并保持一致。如果 "check" 表示检查，就不要同时用它表示约束。
- 每个动作只选一个词并坚持：都用 "start"，不要这里 "start"、那里 "initiate"。
- 流程写成直接命令，不作叙述，也不用被动：“安装组件”，而非“组件必须被安装”。
- 尽量避免英文 "-ing" 形式。

<a id="leave-no-sentence-open-to-two-readings-global-english"></a>

## 不让句子存在两种读法（Global English）

- "only"、"not" 等词紧贴其修饰对象："only fails on growth" 与 "fails only on growth" 意思不同。
- 拆开长名词串："the proto import budget check script" 改为 "the script that checks the proto-import budget"，明确是检查 proto 导入预算的脚本。
- 每个 "it"、"they"、"this" 都必须明确指向一件事。拿不准时重复名词。不要让 "this" 或 "which" 指代整个从句。
- 不省略动词："Phase 1 moves the converters and Phase 2 the runtime" 中，Phase 2 缺少动词。补上它。
- 保留体现结构的小词，例如 "Ensure that the switch is off" 中的 "that"。不要用清晰度交换字数。
- 并列时如果重复冠词能避免误读，就重复：当客户端和宿主是两个事物时，写 "the client and the host"，不写 "the client and host"。
- 句子可能以两种方式分组时，明确 "and" 或 "or" 连接的部分。"Both...and"、"either...or"、"if...then" 都能直接消除歧义。
- 使用句号，不用分号。将长破折号（em dash）改为新句子。
- 括号文字应是完整语法单位或独立句子。绝不以 "(s)" 构造复数。
- 不用斜杠：写“a、b 或两者”，不用 "a/b" 或 "and/or"。
- 同一个事物在各处都使用同一个名称。一份文档把同一事物分别叫“门禁”“棘轮”“预算检查”，会让人学成三个事物。没有改变的内容，不要翻新措辞。
- 避免习语、口语俗语、拉丁缩写和隐喻。

<a id="voice-and-repo-specifics"></a>

## 文风与仓库具体要求

- 对本技能触及的每份文档应用 **unslop** 技能。AI 词汇、填充、保留语气和格式痕迹等模式清单由该技能负责。
- PR 描述和提交消息也是写作。除 Diátaxis 外，所有层次均适用。PR 正文是一份审查者一分钟内能读完的简报。不要粘贴工作群日志、SHA 列表或指标表，使用链接。
- 产品 UI 字符串不是文档，使用产品自身文案规范。
- 代码片段用 Tab 缩进。写真实路径。所有数量或目录树断言必须在落地 commit 中为真，并附重新生成它的命令。
