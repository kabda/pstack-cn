<a id="maintain-a-verification-skill"></a>

# 维护验证技能

应用一变化，功能映射就开始过时。本技能用于维护 `/create-verification-skill` 生成的技能，或任何包含功能映射的项目本地验证技能。严谨性的单位是功能，不是每一句话：从源码覆盖每份功能文件，实际运行每个功能，不必把每个列表项都变成终端命令。

<a id="outcomes"></a>

## 结果

选择并说明一种结果：

- **clean**——每个功能都完成源码和实际运行覆盖，无值得交付的改动。不建分支、不建 PR。
- **changed**——用一个 PR 交付经证明的文档、运行工具或地图修正。
- **blocked**——覆盖无法完成，或已证明的修复无法安全交付。准确说明阻碍。

<a id="edit-scope"></a>

## 编辑范围

只编辑验证技能自己的目录（SKILL.md、features/ 和它拥有的运行脚本）。执行期间绝不能编辑产品代码：地图描述了应用不再具备的行为，可能是文档漂移（修地图），也可能是产品回归（报告，不要用文档掩盖）。

<a id="pass"></a>

## 执行流程

0. **定位目标。** 找到待维护验证技能：正文包含启动、驱动章节和功能映射的项目本地技能，通常是项目技能目录（`.cursor/skills/`、`.claude/skills/`、`.pi/skills/` 或 `.agents/skills/`）下的 `verify-*/`。多个候选则询问选哪个；没有候选则停止，指向 `/create-verification-skill`，不要虚构目标。

1. **索引整理。** 阅读功能映射 README，查找同目录文件。修复缺失、多余、重复或失效条目。保持轻量，不生成清单。

2. **源码调查。** 每个功能文件对应一个只读子代理，同时启动。各自从源码说明“这个用户功能如何工作”，带引用指出可能的文档漂移，并返回一份简明的实际验证步骤。子代理绝不驱动应用，也不编辑文件。返回结构：功能摘要 / 源码入口 / 疑似漂移或无漂移 / 一份操作步骤。

3. **协调。** 每份功能文件都必须有返回摘要。合并重叠步骤，尽量减少所需应用状态。抽查引用的漂移，不重新证明无问题的结论。扫描近期改动，寻找地图缺失的用户界面；只有具体源码路径才能支持“缺失”的判断。

4. **实际运行验证。** 即使源码看起来正确也必须执行。协调者负责全部驱动；遵循验证技能自身的启动模型：服务器和 UI 使用一个长期实例串行驱动，短生命周期 CLI 每次驱动使用新的隔离会话（由该技能的“启动”章节决定，不由本技能决定）。每个功能至少运行一次，并在整个流程、无论发生何种失败时都保持三个不变量：(1) 实例上次出现意外行为后未经健康检查，绝不能继续驱动——首次驱动前诊断，以会话为单位时每个新会话先诊断，每次驱动失败后再次诊断；诊断无法发现的故障（健康进程上卡死的 UI 状态），要重置为已知状态或重启，不要抱侥幸心理；(2) 迄今捕获的证据经每次清理后都保留，在指定位置实际检查，不能假定；(3) 驱动启动的任何内容都不得在失去用途后继续存活——失败迭代的残留必须清理，无论会话卡住、退出还是共享（共享实例只清残留，不清实例）。技能漂移导致诊断失败，也属于漂移：在编辑范围内修复并重试一次，只有被修复内容失效的部分需要重启，不扩大重启范围，然后才能把流程标为 `blocked`。某功能无法到达，只有写出具体前置条件（认证、授权资格、OS、外部状态）和尝试的路线，才可标为 `verified-unreachable`；地图若遗漏该前置条件，就是漂移。分诊产生的任何运行工具修复，都要在交付前重新实际驱动。最终停止清理发生在本次最后一次驱动之后，包括这些重新证明；任何内容都不能比本次运行存活更久，证据按技能要求保留。

5. **分诊。** 用户视角描述错误或缺失 → 文档漂移，修复它。行为有效但运行工具无法驱动 → 运行工具缺口，修复它；运行工具修复遵循与生成时相同的辅助工具规则（脚本可执行，技能正文记录调用方式）。应用行为确实损坏 → 产品缺口，向用户记录，不纳入本 PR。

6. **交付或停止。** changed：先重读每份修改文件，再用一个 PR 交付经证明的修正。clean 或 blocked：不建 PR，如实报告结果和覆盖情况。

在临时位置保留简明运行笔记（覆盖的功能、不可到达的前置条件、已确认漂移、结果），不要提交。
