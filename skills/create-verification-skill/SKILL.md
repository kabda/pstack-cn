<a id="create-a-verification-skill"></a>

# 创建验证技能

每个严肃项目都需要一种脚本化方式，驱动真实应用并证明行为：启动应用，像用户一样操作功能，捕获证据。本技能将这一能力生成为针对仓库定制的项目本地技能（`<skills>/verify-<app>/`）。`<skills>` 是运行环境的项目技能目录：Cursor 使用 `.cursor/skills/`，Claude Code 使用 `.claude/skills/`，Pi 使用 `.pi/skills/`，Codex、OpenCode 等使用 `.agents/skills/`。如果仓库已经在其中某个目录维护技能，就使用该目录。生成内容是写给下一个智能体的，不是写给人：一个从未见过应用的智能体会在任务中途直接阅读它。

<a id="1-interview-the-repo-not-the-user"></a>

## 1. 调查仓库，而不是询问用户

从代码库回答以下问题，只向用户询问无法观察的信息：

- **交互界面：**用户真正接触什么？Web UI、CLI/TUI、桌面应用、API、移动应用、库？仓库可能有多个，选择主要界面并注明其他界面。
- **运行：**应用如何本地启动？优先使用仓库自身文档中的开发命令（包脚本、Makefile、README 快速入门）。注明端口、环境变量、种子数据和认证。
- **驱动：**智能体如何程序化交互？优先使用现有运行工具：Playwright/Cypress 测试、expect 脚本、PTY 辅助工具、可用 curl 调用的端点、调试端口。之后才选择通用方式：Web 与 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY，服务用普通 HTTP。
- **观察：**可以捕获哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离：**两个实例能否并行运行（端口、数据目录、配置档案）？不能就明确写进生成技能：拒绝同时操控共享实例，好过破坏用户会话。

如果当前检出内容无法直接构建或启动，先修复（或准确报告），再生成技能；基于损坏基线编写技能会教出错误步骤。如果无关的缺失资源阻塞启动（API 根本不提供的静态目录、示例配置），生成技能可以创建它，但要明确标为验证脚手架，并在清理时移除。

<a id="2-generate-the-skill"></a>

## 2. 生成技能

编写 `<skills>/verify-<app>/SKILL.md`，包含 YAML frontmatter（`name: verify-<app>`，以及说明应用、交互界面与使用时机的 `description`；没有 frontmatter，技能就不会注册），并包含以下各节。各节均以调查实际发现为依据，不留占位内容：

- **启动：**用于启动验证应用的准确命令，以及判断就绪的方法（日志行、提示符）。启动必须能从空数据目录到达可用状态，包括所有迁移和种子数据。就绪意味着可用，而非进程能响应。数据库健康检查可能已通过，但初始化脚本仍在运行。包括停止和清理方式。短生命周期的 CLI 或 TUI 无需常驻服务器：启动意味着只构建一次二进制文件（或安装依赖），随后每次驱动都在独立隔离的 PTY 或 tmux 会话内启动。
- **诊断：**一项只读检查，回答“这个实例值得驱动吗？”——进程运行、版本或构建正确、端口归我们所有、认证有效。只要出现异常，智能体先运行它。
- **驱动：**使用仓库中的真实选择器和命令给出操作方法，而非泛泛示例。优先采用稳定定位方式（ARIA 标签、data 属性、提示字符串、路由路径），而不是坐标和 Tab 顺序。
- **证据：**说明证明需要捕获什么、存在哪里。陈述证明标准：操作真实用户路径，而非内部 setter 或仅测试使用的端点；捕获动作及其结果状态，而非只截最终屏幕；除可见结果外，还验证副作用（写入的文件、插入的行、发送的消息）；只有生产边界已经隔离外部系统时才使用 mock。安全路径为 dry-run 或测试模式时，通过观察文件、网络、Git 引用来验证实际跳过什么，不要相信名称：有些 dry-run 仍会访问网络或打开浏览器。
- **清理：**说明如何停止并清理此次运行创建的实例。绝不能按进程名批量终止，只终止自己启动的内容。清理移除实例和临时状态，绝不移除证据：证明产物在清理后仍保留，技能必须注明位置。
- **辅助工具：**技能附带的所有脚本都必须可执行，并在技能正文展示调用方式。需要读者反向研究才能使用的工具不算辅助工具。

<a id="3-seed-the-feature-map"></a>

## 3. 建立初始功能映射

创建 `<skills>/verify-<app>/features/README.md`，并为每个可识别的用户功能创建一个文件（从路由、命令、菜单或文档入手，初期以最重要的 3–5 个为目标）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 的结构：README 索引，每个功能一个文件。每份文件从用户视角回答：功能是什么、如何进入、如何用运行工具驱动，以及什么可观察的最终状态能证明它有效。四个 H2 标题必须为 `Sub-features`（子功能）、`How to get to it (user POV)`（用户如何进入）、`Driving it with <harness>`（使用指定运行工具驱动）、`Gotchas`（注意事项）。如果种子数据不满足用户旅程的前置条件，该旅程应报告失败，并把原因写入该功能的 `Gotchas`。绝不能削弱旅程要求来让它通过。功能映射是仓库持续维护的验证来源；如果地图列出多个入口，只驱动一个方便入口的证明就不完整。

<a id="4-prove-the-generated-skill-before-handing-it-over"></a>

## 4. 交付前证明生成的技能

完整执行一次技能自身的指令：启动、诊断、驱动一个已映射功能（一个就够；地图让后续运行能够覆盖其余功能）、捕获证据、清理。清理后，确认指定位置的证据仍然存在；如果清理吞掉证明，本步骤失败。修复失败处，每次失败迭代后也要执行生成的清理步骤，避免失败尝试遗留进程和端口。从未执行过的生成技能只是草稿，不是交付物。如果用替代环境证明真实目标（用容器代替新虚拟机、本地服务栈代替远程服务栈），列出替代环境做了、而真实目标不会做的每个设置步骤。这些步骤在真实目标运行覆盖之前，均保持未验证。

<a id="5-offer-the-maintenance-loop"></a>

## 5. 提供维护循环

引导用户使用 `/maintain-verification-skill`，在应用变化时保持功能映射准确。只有用户询问时才建议维护频率。
