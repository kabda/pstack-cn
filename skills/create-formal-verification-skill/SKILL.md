<a id="create-a-formal-verification-skill"></a>

# 创建形式化验证技能

测试检查的是有人想到要编写的案例。形式化验证检查指定范围内的所有案例：模型中步骤的每种顺序、边界内的每个输入，或所有输入。本技能找出仓库中最需要这一能力的部分，验证其中一个性质，并留下项目本地技能，让下一个智能体能够依据该性质检查改动。技能应面向一个在改动中途直接阅读、从未见过你工作的智能体。用户必须无需学习验证语言，就能信任结果并据此行动。

<a id="choose-the-target-from-the-code"></a>

## 从代码中选择目标

从代码库回答问题，只向用户询问无法观察的信息。如果用户指定区域或缺陷，从那里入手。

好的目标是代码作出的一项承诺：违背它会伤害用户，而测试很少覆盖会使承诺失效的情况。选择仓库中最符合这一特征的目标，而非最容易验证的目标。

<a id="let-the-question-choose-the-tool"></a>

## 让问题决定工具

选择以最低成本回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器或其他工具。事件是否可能按坏顺序发生，通常适合对小型设计模型做模型检查；对任何语言，这类问题默认选择 TLA+。代码本身是否对每个输入都正确，例如内存安全、溢出或数据结构不变量，通常适合直接作用于代码的验证器。如果没有验证器支持该语言，明确说明，用生成输入测试真实代码，而不是手写函数模型。若性质必须对任意规模成立、有限边界不够，可能需要证明。优先选择仓库开发者能安装和运行的工具，并向用户说明选择理由。

<a id="what-makes-it-good"></a>

## 优质验证的要求

- **忠于代码。** 模型或证明的每个部分都指向审查者能打开的代码。验证中视为不可分割的一步，在代码中也必须是不可分割的一步。名称来自本仓库。
- **能够失败。** 从未见过失败的检查不能证明什么。针对它保护的代码制造错误变体，例如移除检查或重排步骤，展示每个性质如何失败。
- **问题仍然是问题。** 当前代码违背性质时，用代码自身的概念描述反例并报告。不要削弱性质或模型直到通过；除非用户要求，否则不要修改产品代码。
- **如实说明范围。** 说明验证内容、边界与假设，以及未覆盖内容。通过只覆盖模型或指定边界，不代表整个系统。
- **无需懂工具也能读懂。** 各用一句通俗的话说明性质与危害。用代码中的说法，将反例讲成简短步骤序列。
- **重跑成本低。** 一条命令、可复现工具版本，以及足够短的运行时间，让下一个智能体愿意在每次相关改动时运行。
- **与代码保持同步。** 记录每项检查覆盖的文件和函数，以及上次确认验证准确描述代码的 commit。此后受覆盖代码发生变化时，下一个智能体能够看出验证需要复查。

<a id="generate-the-verify-skill"></a>

## 生成验证技能

编写项目本地技能，frontmatter 指明区域和使用时机。没有 frontmatter，技能不会注册。仅凭技能，下一个智能体必须能够判断改动是否触及已验证代码、运行检查、区分真实缺陷与建模错误，并在有意改动时更新验证。把覆盖记录和同步 commit 写进技能，并要求下一个智能体只有确认验证准确描述新 commit 的代码后，才能推进同步 commit。使用仓库真实命令、路径和名称，不留占位内容。

如果检查使用 TLA+ 模型，要求下一个智能体用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能阅读每次结果。它会用通俗语言，以最短路径展示检查器发现的每个不变量违规。检查通过时，`/statechart` 绘出系统状态转换图。按名称引用 `/statechart`。其命令、选项和文件路径会随版本及机器变化，因此不要把这些内容复制进生成技能或脚本。

<a id="prove-it-before-you-hand-off"></a>

## 交接前证明

像下一个智能体那样，按生成技能执行一次，并对真实代码作一项破坏性质的临时改动。它必须捕获破坏。随后丢弃临时改动，确认检查恢复初始结果：通过，或仅因你将报告的问题而失败。从未运行的验证技能只是草稿。如果技能漏掉破坏，或某个步骤无法执行，修复技能或验证，不要修改临时破坏来迁就它。

<a id="hand-off"></a>

## 交接

告诉用户验证了什么、使用何种工具及原因、边界、检查发现（用通俗语言）、运行方法，以及未覆盖内容。只有发现另一个相近目标时，才建议第二目标。指向 `/maintain-formal-verification-skill`，用于在未重新检查的改动后，使验证重新与代码一致。
