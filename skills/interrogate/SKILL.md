<a id="interrogate"></a>

# 对抗审查

对抗者尝试破坏一项改动或设计。只有实际运行证明的问题才能保留。报告问题，不要实施修复。

<a id="frame"></a>

## 界定任务

以用户指定的范围为准。否则，范围是从当前分支与基分支的合并基点开始、一直包含工作区的分支 diff。根据用户消息、提交和 PR 描述，使用 **in-your-own-words** 技能陈述意图。意图不清时询问用户。

<a id="fan-out"></a>

## 展开并行

运行 **arena** 技能的阶段 A 第 3、4 步和阶段 B，但作四处调整。读取 `interrogate reviewers` 行，替代 `arena runners`。把范围内尚未提交的改动复制到每个 Git 工作树。每个对抗者都以通用子代理启动（Cursor 中为 `generalPurpose`）。不给 arena 任务与设计理由，而是向每个对抗者提供范围、意图，以及以下说明：

> 尝试破坏这项改动。每个问题都必须通过对真实代码的运行来证明，例如失败的测试、复现脚本，或显示错误行为的命令输出。对于设计或计划，运行原型或探测当前代码树。复现材料留在你自己的 Git 工作树中。每个问题都要报告标题、精确命令、实际输出，以及符合意图时应有的输出。没有实际运行的内容一律不列出。这也包括风格、命名、结构，以及只有未来改动才会使其产生影响的风险。没有发现问题也是有效结果。

<a id="verify"></a>

## 验证

按 arena 阶段 F，重新运行每个问题的命令来验证。输出确实显示失败、且失败违背意图时，才保留问题。其余丢弃。合并根因相同的问题。

跳过 arena 的阶段 C、D、E。不同对抗者会发现不同故障，因此结论应保留所有经验证的问题，而不是只选一个对抗者的清单。

<a id="output"></a>

## 输出

- **意图**：重述内容。
- **问题**：每个已验证问题的命令、输出、如何违背意图，以及发现它的对抗者。如果没有任何问题保留下来，写明“没有经验证的问题”。
- **丢弃项**：按对抗者列出被丢弃问题的数量和原因。
