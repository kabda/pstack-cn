<a id="tdd-bug-fix"></a>

# TDD 缺陷修复

修复具有清晰、低成本测试路径的缺陷时，先让错误行为能够通过执行复现，再修改生产代码。目标是一个聚焦的回归测试，在修复前失败、修复后通过。

不切实际时，不要强行添加测试。如果现有测试需要大范围搭建运行环境、脆弱的 mock、缓慢的端到端基础设施、仅生产环境存在的状态、含糊的复现步骤，或大规模改动无关测试夹具，就跳过新增测试，改用最接近且有用的验证方式。

<a id="workflow"></a>

## 工作流

1. **理解缺陷。** 明确预期行为、当前行为、受影响路径，以及最小可观察复现。
2. **选择范围最小的可执行检查。** 优先使用该代码路径已有、最接近的单元、组件、集成或回归测试。如果没有明显可行的测试路径，不要仅为满足流程而从头创建一套。
3. **先写失败测试。** 增加能够捕获该缺陷的最小聚焦测试。测试应表达预期行为，而不是照搬当前实现。
4. **修复前运行新测试。** 确认它因预期原因失败。如果它通过，或因无关原因失败，先纠正测试或复现，再编辑实现。
5. **修复缺陷。** 对生产代码作最小改动，满足预期行为，同时保留相邻约定。
6. **重新运行回归测试。** 确认测试现在通过。

<a id="if-a-failing-test-is-impractical"></a>

## 无法切实编写失败测试时

改用最接近的可执行回归检查：定向脚本、手动复现命令、浏览器自动化、快照对比、日志断言或聚焦的集成检查。

宁可不新增测试，也不要写糟糕的测试。糟糕的测试包括：主要测试 mock；固化当前实现细节；依赖时序或无关全局状态；为了小修复需要昂贵基础设施；或证明修复后会立刻被删除。

<a id="guardrails"></a>

## 边界要求

- 不要仅为匹配错误实现而更改测试。
- 除非预期行为确实改变且理由明确，否则不要削弱现有断言。
- 回归测试只聚焦该缺陷，避免大范围改动测试夹具或无关地扩大覆盖范围。
- 如果缺陷偶发，应尽可能使测试确定可重复，并记录要锁定的信号。
- 如果缺陷暴露了一整类更广泛故障，先落地聚焦的回归路径，再考虑覆盖其他同类情况。

<a id="final-response"></a>

## 最终回复

报告证据，不只报告结果：

- 写明修复前失败的测试或可执行检查，以及实际产生的失败。
- 写明修复后通过的测试运行，以及执行过的相关验证。
- 如果无法展示修复前失败的证据，说明原因，并描述替代使用的最接近回归检查。
