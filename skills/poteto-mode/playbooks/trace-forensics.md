### 追踪数据取证

**你负责根据产物作出诊断。**

不同于对实时进程插桩的 **Runtime forensics**。这里捕获物已存在，它是固定数据集，读取它，不要重跑。保持工具通用，例如 cpuprofile 和 `.json.gz` 用 DevTools 或 trace 解析器，spindump 用文本编辑器，heapsnapshot 用堆工具。

1. 识别格式，用正确工具加载。大型产物交给子代理解析，参见 **principle-guard-the-context-window** 技能；主对话保留提炼后的发现。按“子代理”一节选择各自的推理级别及 fast 或标准速度。
2. 将原始产物变成可查询形态。把追踪数据或堆快照导入 sqlite，每个样本、栈帧或节点一行。先形成可查询结构，再阅读。
3. 缩小到原因。查询耗时最多的栈帧，沿调用树走到热路径。泄漏则沿泄漏对象到 GC root 的保留链追踪。spindump 则找到持续占用 CPU 或阻塞的线程及其等待原因。
4. 归因到源码。通过产物自身符号，将热栈帧映射到文件、符号和行。没有源码映射的栈帧还不算诊断。解析符号，或明确说产物不带符号。
5. 有成对捕获物时，比较前后产物确认。否则把发现标为产物支持的最强假设，不称为已确认原因。
6. 交回有证据引用的诊断，未被要求则不修复。原因明确后路由到 Bug fix（缺陷修复） 或 Perf issue（性能问题）。吞吐量检查点保持一行：`throughput checkpoint: n/a, read-only forensics`（吞吐量检查点不适用，本次为只读取证）。

**回复：** 产物和格式、提炼后的发现、源码位置、产物路径，以及是否由成对捕获物确认。
