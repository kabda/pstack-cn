### 缺陷修复

**任务由你负责。规划、审查、验证。** 把调查和修复委派给子代理，自己保持主导。按“子代理”一节，为每个子代理选择合适的推理级别及 fast 或标准速度。

遵循科学方法。交付的每行代码都要能追溯到运行时证据。只是“也许有用”的多余防护是假设，不是修复，不能交付。证据推翻假设时，回退由它引出的改动。只交付证据支持的最小改动，不多做。

1. 通过控制技能（“不可妥协的要求”）亲自在对应界面复现，即使调试或插桩协议要求让用户复现。只有明确说明控制界面无法触达目标的具体原因，并已把它操作到极限后，才能要求用户。如果无法直接复现，就构造触发条件、收紧条件或插桩，直到触发。
2. 二分查找原因。提出候选假设，逐一排除，直到只剩一个。通过对受影响子系统运行 `how`，以及用 **why** 技能调查回归历史，形成初始假设。每轮选择能切掉最多剩余问题空间的分割，获取运行时证据并排除。程序状态不清楚时，添加插桩或日志，在运行过程中阅读。不要猜。长期或顽固的排查用 Cursor 的 `/loop` 命令推动。在第 3 步 architect/interrogate 并行分发之前，用运行时证据确认最终留下的*机制*。
3. 规划修复。跨越函数边界时先用 `architect`。给子代理明确范围，使用配置的 bug-fix 模型委派实现，默认 `grok-4.7-xhigh-fast`。
4. 在同一界面验证。原始复现现在通过。“无法定论”或界面不对都不算通过，要明确标出。单元测试只能说明分支行为，不能证明缺陷不存在。
5. 安排提交，让失败复现在 Git 历史中先于修复落地。缺陷有低成本本地测试路径时，参见 **tdd** 技能的先失败测试节奏。测试成本高、重度依赖集成或路径不明时跳过。
   这是 **sequence-verifiable-units** 原则技能的典型应用，先放失败测试，再叠加修复。
6. 执行 **Opening a PR（创建 PR）**。

**回复：** 损坏了什么、根因、修复、如何验证。原样粘贴复现先失败后通过的输出。
