### 完全自动驾驶

**你负责裁决，绝不负责 PR。一名负责人带每个 PR 从构建走到合并；在从未编写该代码的 swarm 证明将要落地的代码之前，任何 PR 都不得合并。**

一个裁决覆盖一个补丁，全绿 CI 覆盖一个 head。第 4 步完整运行一次 swarm，之后仅重大改动才再运行。`playbooks/shipping.md` 的 patch-id 规则可延续某条验证通道的结果，而每个新 head 都需要自己的全绿 CI。

1. **操作者的门禁优先。** 授权只覆盖队列中的项目，因此操作者指定由自己决定的项目，以及队列之外的 PR，都停在可合并状态。要求说明计划不等于准许开始。
2. **每个 PR 创建一名负责人，把工作保存在替补者找得到的地方。** 整个计划只解析一次代码托管平台。默认使用 GitHub CLI（`gh`）。若 `command -v origin` 成功且 Origin 能解析仓库，所有 PR 操作都用 `origin pr`；否则继续用 `gh` 并记录回退。绝不要求 Graphite（`gt`）。每名负责人都是 Cursor 云端智能体，负责构建、按 `playbooks/opening-a-pr.md` 创建 PR、在真实交付物上证明改动、按 `playbooks/babysit.md` 跟进至全绿，并在第 4、5 步放行后合并。

   尽早创建 PR，让 CI 和机器人与工作并行。代码只有完成去套话处理，即 `cursor-team-kit` 插件的 `deslop` 技能（`/deslop`），以及 `/no-comments` 检查后才算就绪，因此完整 swarm 在成品代码上运行。随后 rebase 到当前主干，在自行证明之前报告代码就绪的 head，让验证在补丁实际落地的基线上运行。报告之后的每个 head，并在自行证明、CI 和 babysit 都完成后报告可合并。修复轮次保持该基线，除非主干产生冲突、破坏 CI，或已有已知并发改动落到了相同文件，因为每次 rebase 都会重启 CI。在代码就绪推送之前，以及之后每次需要验证器的推送之前，在已提交的 head 上运行仓库对改动路径要求的检查。

   假设虚拟机随时会失效。开始后尽快推送，并按 **show-me-your-work** 技能在根智能体的存储位置（系统提示中的路径）建立决策轨迹；每个单元完成后先推送，再开始下一个。谁创建子代理，谁就在该存储中记录它的 ID、状态，以及依据同类历史运行设定的停滞时间阈值，便于父智能体失效后根智能体探测它。只对自己的分支 force-push，并使用 `--force-with-lease`，锁定到自己最后一次推送或接管的 SHA；出现任何不是自己发起的推送时，停止并报告根智能体。
3. **负责人并行地从主干出发，绝不堆叠，** 让每个 PR 独立落地。
4. **进行一次 swarm 验证。** 完整 swarm 在代码就绪 head 上运行一次。只有新增行为、重新设计或大幅新增 diff 才再次完整运行。rebase、解决合并冲突或小修复，只需在新 head 上用一个验证器；纯措辞修改不需要。按 **swarm** 技能，在代码就绪 SHA 上并行分发独立验证器。它们重跑门禁，通过对应控制技能（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或具名驱动，在真实界面上实时证明关键行为，并审计 diff。缺少实时验证通道，或你尚未核验可合并报告的凭据时，裁决都不算干净，因为任何通道都不信任自己没检查过的主张。

   只有能展示的问题才能阻塞 PR，证据可以是该 head 上失败的运行，或被 PR 改错的文档行。PR 基线本就存在的问题，无论基线是主干还是栈中下层 PR，都不阻塞，除非该 PR 复制它或新触发它。只有用户会遇到的缺陷、失败门禁或错误的已交付文档才阻塞；其他都放入后续项。
5. **负责人只合并你已验证、且在实际落地主干上测试过的内容。** 仅 CI 全绿绝不授权合并。swarm 各通道启动后，合并准备阶段 rebase 到当前主干、报告新 head，并等待 CI 全绿。

   合并前立即 fetch 主干，判断它的变化是否会影响补丁，因为每次主干前进都 rebase 会永无止境。将落地的代码从未测试过时，例如出现冲突、双方都改了一个文件，或变更影响了 PR 应运行哪些检查，就 rebase 并等待 CI。双方都修改 lockfile 时，如果对合并结果执行冻结安装能通过，且 PR 改动的包在其中解析结果与 head 一致，则无需 rebase，因为该安装已测试将要落地的 lockfile；安装失败就意味着必须通过 rebase 修复。主干修改了补丁的调用方或依赖项，例如被调用代码或依赖版本时，在合并结果上运行补丁的检查，通过后再合并。其他情况直接合并。如果主干将迫使合并准备之后发生第三次 rebase，就保持并报告根智能体，由它安排相互碰撞的工作顺序。
6. **运行根层控制。** 任何放宽门禁的内容，例如提高预算或增加允许列表项，都需要验证器证明，再由你重新会签，因为负责人正是想让检查全绿的人。授权覆盖审批时，该会签就是批准，负责人的批准记录应指向你的会签，供验证通道核查。禁用检查或把失败降为软失败的改动一律移除，因为这会使检查无法再守住所有情况。绝不代为给出或绕过托管平台强制要求的审批，因为任何会签都不能覆盖它。

   操作者许可后，启用 `/loop 1h` 持续审计，直到没有委派工作剩余，因为长时间执行会偏移，智能体也会悄悄停滞。每次心跳从主干重读本操作手册，并通过让负责人补记记录来修复偏移，例如未报告的 head 或未登记的智能体，因为偏移是记录缺口，不是停滞。探测每个智能体，一直追到叶级通道，并根据实际副作用判断，因为状态文字和摘要可能掩盖卡住的子智能体。智能体报错、无法开始新轮次，或超过其停滞时间阈值仍无新进展，就属于停滞；负责人到首次心跳仍既未推送也未写轨迹行，同样如此。正在等你或操作者的不算停滞，要回应它。发现停滞立即替换，不等停止命令生效。如果心跳带来了操作者需要知道的变化，以 **ketchup** 技能更新其情况；没有变化则保持安静。
7. **操作者要求停止时立即收手。** 保持指令向每名负责人传达为零写入命令。各自报告当前状态，并保留任务说明，直到操作者解除保持。

**回复：** 按 **ketchup** 技能向操作者更新情况，包含各 PR 状态及裁决、已合并内容、会签及原因、待操作者决定的门禁、搁置的后续项，并附各 PR 与决策轨迹链接。
