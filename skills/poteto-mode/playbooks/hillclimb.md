### 爬坡优化

**指标和实验完整性由你负责。监督并审查，委派尝试。** 用于持续迭代地让一个可测量项目逼近目标。一次性修复使用 Bug fix（缺陷修复） 或 Perf issue（性能问题）；这里是循环优化。

核心纪律是一次改动、一次测量、保留或回退。绝不堆叠未经测试的改动，绝不通过查看代码宣称获胜，参见 **prove-it-works** 原则技能。

1. 选择指标前，先弄清工作负载和架构。对目标运行 **how** 技能，点明能影响结果的真实负载维度，例如数据量、历史、状态、并发，并选择能复现用户抱怨的用例。如果没有用例能复现，就修复复现方式，不要开始爬坡优化。然后固定一个指标、何种方向算更好，以及可检查的停止谓词。该谓词同时包含目标和最低尝试次数，避免一次幸运的早期胜利就结束运行，例如“至少比基线改善 50%，且至少 10 轮迭代”。用户给出数字时采用其数字，否则先协商。
2. 构建测量工具，证明它的敏感性，再冻结它，参见 **build-the-lever** 原则技能。运行具有对照差异的真实负载，确认目标用例能复现症状，较容易用例按预期拉开差异。如果工具无法区分它们，就修改负载或指标。冻结前用 **benchmark-checklist** 技能核验工具，让它打印错误数和已完成工作量。冻结后，由一个可重复命令输出指标，并充分采样以超过噪声，例如 N 次中位数，而非单次运行。任何改动之前，记录基线指标，并记录回归门禁的一次全绿运行，即必须保持通过的测试。
3. 通过 **show-me-your-work** 技能创建决策日志。使用 `decision.tsv`，每次尝试一行，包含 `id`（编号）、`hypothesis`（假设）、`change`（改动）、`before`（改前）、`after`（改后）、`delta`（差值）、`tests`（测试）、`verdict`（值为 `kept` 或 `reverted`，即保留或回退）、`note`（备注）。每次尝试前先读。将它留在版本树之外，用 gitignore 忽略。
4. 每个假设都要基于第 1 步的架构模型，指明具体机制，例如“把 X 延后移出启动路径，因为它阻塞首次绘制”，而非“试着 memoize 点什么”。性能指标的假设按 Perf issue（性能问题） 操作手册第 2 步的性能口诀排序（`playbooks/perf-issue.md`）。只借用顺序，不借用那一步的停止规则。
5. 循环，每轮一个假设：
   - 把改动交给使用配置 hillclimb 模型的子代理，默认 `grok-4.7-xhigh-fast`，范围严格限定。按“子代理”一节选择各自的推理级别及 fast 或标准速度。监督并审查 diff，而非亲自输入代码，参见 **guard-the-context-window** 原则技能。有多个独立假设时，分发给并行子代理，每个使用独立 Git 工作树，参见 **separate-before-serializing-shared-state** 原则技能。
   - 用冻结工具测量前后结果，并运行回归门禁。
   - 只有指标变化超出噪声且门禁保持全绿时才接受。否则完整回退改动。只是“也许有帮助”的调整不保留。
   - 每个接受的修复单独提交，只暂存自己修改的文件，使用 `git add <files>`，绝不用 `-A`。无论保留还是回退都记录一行。
   每轮结束先检查，再开始下一轮，参见 **sequence-verifiable-units** 原则技能。无人值守时，只借用 Autonomous run 操作手册（`playbooks/autonomous-run.md`）的唤醒机制，不借用其停止规则。
6. 突破第一个平台期。停滞或连续几次拒绝后，先转换类别、组合差一点成功的方案、重读源代码或尝试更激进方案，再判断是否已登顶。正确性和简单性比数字更重要。破坏行为的改善要回退，保持数字不变的简化可以保留，参见 **laziness-protocol** 原则技能。
7. 谓词满足，或剩余想法收益边际太小、不值得成本时停止。不要放宽谓词以求达成；还有便宜且未试的假设时，不要退出。卡住时上报，不要空转。
8. 执行 **Opening a PR（创建 PR）**，按落地顺序堆叠已接受的提交。

**回复：** 指标和目标、基线到最终值及百分比差异、迭代次数（保留与回退）、每项接受修复各一行、`decision.tsv` 路径，以及如果继续推动最想尝试的下一项想法。
