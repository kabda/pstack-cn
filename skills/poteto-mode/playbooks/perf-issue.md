### 性能问题

**测量叙述由你负责。规划、审查、验证数字。** 每项修复都与测量关联，不要用读源代码代替测量。

1. 通过对应控制技能捕获基线追踪数据。用 **benchmark-checklist** 技能核验基线及之后的每个数字。
2. 用 `how` 为假设打下依据。未经实际运行，不宣称性能上限。
   按顺序尝试性能口诀，从成本最低的开始：
   1. 不做。停止无人使用结果的工作，而非降低它的成本。
   2. 做，但不重复做。
   3. 少做。
   4. 晚点做。
   5. 趁他们不注意时做。
   6. 并行做。
   7. 更便宜地做。

   较前面的口诀达到目标时就停止。
3. 根据追踪数据规划修复。跨函数边界时先用 `architect`。使用配置的 perf-issue 模型委派给子代理实现，默认 `grok-4.7-xhigh-fast`。按“子代理”一节选择每个子代理的推理级别及 fast 或标准速度。审查 diff，捕获修复后的追踪数据。
   应用 **sequence-verifiable-units** 原则技能，每次尝试验证后再做下一次。
4. 解析并比较产物，例如 JSON 转 sqlite、diff。“无法定论”或界面不对都不算通过，要明确标出。
5. 在 PR 中引用测量。
6. 执行 **Opening a PR（创建 PR）**。

针对一个指标持续改善，而非一次性修复时，使用 Hillclimb 操作手册（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、差值、产物路径。
