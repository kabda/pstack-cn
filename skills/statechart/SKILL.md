<a id="statechart"></a>

# 状态图

图表用读者的语言展示系统如何在状态之间转换。由这个人，也就是读者，决定行为是否正确。

<a id="run"></a>

## 运行

在仓库外的临时目录工作。编写 TLA+ 规格及配置，然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，因此使用能执行 TypeScript 的运行时。

首次运行会通过 mise 安装 TLC 和 Java，需要网络。

<a id="write-the-spec"></a>

## 编写规格

- 读者同意的每条规则都写成 INVARIANT。规则可以涉及屏幕、结果、存储值或消息。如果模型没有表示某条规则的变量，就增加变量。绝不能削弱规则来使其成立。
- 把 `Next` 写成动作的析取，例如 `YouPressPlay \/ YouPressStop`。否则 TLC 会将每一步都命名为 `Next`。
- 没有出边的状态会违反 `NoDeadlock`，即使它是正确的终止状态。已有 INVARIANT 或 PROPERTY 使用该名称时，规则名改为 `CHECK_DEADLOCK`。向 `Next` 增加一个仅在终止状态成立、且不改变任何值的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 中给它标签。

<a id="pick-the-chart"></a>

## 选择图表

需要判断的工作由你完成：每个状态和箭头的措辞、阶段及其颜色、标题，以及面向读者的报告。将这些工作放进 view 模块，用 `--view` 提供。

为了展示读者的语言，view 导出 `state(vars)`。`state()` 返回值决定图表形式：

- 字符串生成扁平图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组生成父级状态：`export const state = (v) => v.main.split(".");`
- 对象为每个键生成一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

给状态使用读者可见或关心的标签，例如“正在付款”或“已持有租约，等待写入”。标签不使用变量名。在 `vars` 中，TLA+ 序列是键从 1 开始的对象，因此 `v.pc[1]` 对应 `pc[1]`；集合是数组。

view 还可以导出 `step(action, from, to)`。它接收 TLC 动作名及步骤前后的值，返回箭头标签。每个步骤标签都按用户看到的发生过程来写，例如“你按下播放”或“连接失败”。不要使用代码或 TLA+ 动作名称。在图上以相同方式结束的两个动作使用同一标签，从而共享一条箭头。

某步骤仅在部分条件下发生时，以读者的语言在标签末尾用方括号注明条件，例如 `you press play [while the file loads]`（你按下播放［文件仍在加载时］）。区域图中，命令会用其他区域的标签语言，把这些区域上的条件写在箭头上，例如 `[when Offline]`（离线时）。你写的方括号会替代它，导致同一状态发出的两条箭头可能看起来一样。因此在区域图中，不要为另一区域上的条件写方括号。如果某个未在标签中显示的值决定步骤去向，就在标签中写出结果，例如“读取名单失败”。

view 还可导出：

- `group(vars)`：返回阶段名。每个图表状态采用所属组的颜色。一个图表状态背后若包含不同组的模型状态，它就不着色。
- `colors`：为每个组名指定颜色 class。
- `title`：图表顶部显示的字符串。

命令对每个模型状态最多调用一次 `state()`、一次 `group()`，对每个步骤最多调用一次 `step()`。图表和报告共同使用这些结果。因此每个函数都只依赖自身参数。

图表不会绘制起点和终点标签相同的步骤。读者必须看到这一步时，拆分标签。

尽量控制在约 20 条或更少箭头，因为更繁忙的图难以阅读。先让 `state()` 返回更粗粒度的标签。行为相同的值用同一标签，省略读者不需要的细节，例如返回时不改变任何内容的进行中调用。保留缺陷路径的每个状态，以及每个标记。合并把 `breaks` 状态变为 `mayBreak` 时，会掩盖规则在哪被违反。不要合并违反不同规则的两个状态，否则读者看不出哪条规则在哪失效。如果图仍过于繁忙，让 `step()` 对读者不需要的步骤返回 `null`，例如每个状态都有的重置，或箭头信息与其他箭头重复的步骤。隐藏步骤时遵守：

- 保持每个图表状态都能从起始状态沿箭头到达。
- 模型中有出边步骤的每个图表状态，至少保留一条出边。
- 一条箭头对应的所有步骤要么全部隐藏，要么全部保留。只隐藏其中一部分，会缩小它的条件。
- 交接时说明图表隐藏了哪些步骤。

<a id="read-the-report"></a>

## 阅读报告

- 图中违反规则的状态使用 `breaks` class。如果背后仅部分模型状态违反规则，则使用 `mayBreak`。图例说明每种标记涉及哪些规则。两条规则被违反时，两者会写在一个标记上，因此交接时要说明哪个状态违反哪条规则。区域图中，如果包含某区域状态的每种区域状态组合都可能违反规则，该状态会得到标记。如果某组合可能违反规则、但组合中没有状态已有标记，则给该组合的每个状态都加标记。
- TLC 会继续探索违反规则的状态之后，因此图会显示缺陷之后的状态。
- 由于 TLC 会越过缺陷继续探索，无状态数量限制的模型可能无限运行。保持常量较小，或增加 CONSTRAINT。
- 使用 VIEW 或 SYMMETRY 时，TLC 将其视为相同的状态只计一次，图也绘制该单一状态。箭头可能指向它，而非该步骤真正到达的状态；报告会说明这一点。
- TLC 会检查越过 CONSTRAINT 或 ACTION_CONSTRAINT 的每个状态中的规则，但不会探索该状态，也不检查它是否死锁。当某规则的 TLC 最短路径在这种状态结束时，图会绘出该状态，报告给出路径。图不绘制越界的其他状态。这种状态中的死锁不会显示。TLC 也会检查被 ACTION_CONSTRAINT 排除的每步之后的规则，即使通过其他方式已到达下一状态。当某规则的 TLC 最短路径以这样的步骤结束时，图会绘出该步。
- 命令以原配置、一个工作者运行 TLC 检查规则。某条规则被违反时，移除它并再次运行 TLC，直到没有规则被违反。首次违规之后，每次运行在 100,000 个不同状态处停止，避免大型模型无限运行。达到该边界或因错误停止时，报告在 “Rules not checked”（未检查规则）下列出尚未检查的规则，图不标记它们。未检查规则可能成立，也可能被违反。要检查它，从配置移除已违反的规则，或缩小模型。状态边界会增加一个模块，改变 TLC 的变量顺序，因此对于性质，TLC 可能发现与无边界运行不同的反例。
- `tlc.out` 是 TLC 使用原配置打印的输出。如果图未显示某条违规规则的缺陷路径，`tlc-RULE.out` 是找到该路径那次运行的 TLC 输出。TLC 重复首条警告时，普通 TLC 打印两次，`tlc.out` 却只显示一次，因为 TLC 从本命令读取的输出中省略了第二份。只有 Java 使用 `-XX:+UseParallelGC` 时才会如此；否则 TLC 首条警告是建议传入该参数，并且只打印一次。

<a id="show-the-chart"></a>

## 展示图表

以 `mermaid` 代码块向用户展示 `chart.mmd`。图表预算为 500 个状态，以 TLC 原配置计数为准。超过后，图只绘出到达违规规则的路径；若没有规则被违反，命令不会写入 `chart.mmd`。它仍检查每条规则，报告给出状态数量和每条缺陷路径。要查看完整图，缩小模型。

用 Pele 渲染图表。用户要求图片，或图过大而难以阅读文本时，遵循 `references/render.md`。除非用户要求，否则不要使用其他渲染器。

<a id="hand-off"></a>

## 交接

将每份图表及 Mermaid 文本交给需要作决定的人。每个缺陷增加一行：规则、读者对规则的表述，以及报告中的路径编号。说明模型未包含什么。给出重新生成文件的命令，使用新的 `--out` 目录。

模型描述代码时，在真实代码上以测试或实际复现逐步重放每条缺陷路径，每个动作一步。如果缺陷未出现，先认为模型有误，直到证明不是如此。
