# 把工作拆为可验证单元

把工作排成小单元序列，每个都以可检查状态结束；当前单元全绿之前不推进。

**原因：** 在引发问题的单元处捕捉损坏，定位成本很低；整批结束后才发现，问题会被埋没，而且已经在坏基线上继续构建。把同样单元组织为审查者可重放的交付顺序，就把“相信我”变成“看它先红后绿”。

**执行。** 批量处理、迁移或任何一系列类似编辑中，每次改动验证后再开始下一个。每个单元都是前后对照：已知正常状态、一次改动、运行检查，再推进。先 rebase 到干净主干，让每次检查都对照真实基线。工具执行编辑时，逐单元检查几乎没有额外成本，仍然运行它。

**交付。** 按能证明工作的顺序堆叠提交和 PR。典型形态是先失败测试，再叠加修复。其他叙事顺序包括先删减后调整形态、先捕获基线后施加改动、先基础骨架后功能。每个提交都能独立落地，序列读起来像一份论证。

本原则在顺序上补充 **prove-it-works** 原则技能，后者确保每次检查真实；也补充 **build-the-lever** 原则技能，后者降低逐单元检查成本。
