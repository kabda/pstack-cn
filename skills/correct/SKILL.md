<a id="correct"></a>

# 纠正

操作者不断因为同样的错误纠正这个仓库里的智能体。改变仓库，让下一个智能体无法再犯这些错误。

假定每个贡献者都是智能体，只能看到自己打开的文件，会照抄最近的示例，并选择能够编译的最短路径。仓库的设计应当保证：从单个文件看来正确的改动，对整个仓库也正确。

<a id="find-the-mistake-classes"></a>

## 找出错误类别

先阅读近期提交、回滚、审查评论、智能体指令文件，以及解释变通方案的注释。将错误归类。同类错误发生两次，才算一个类别。

<a id="fix-each-class-at-the-highest-level-that-works"></a>

## 在能够奏效的最高层级修复每一类错误

1. **用架构消除错误。** 每份状态只有一个所有者，每项任务只有一种受支持的做法。隐藏内部实现，让错误的导入直接失败。用单一事实来源替代人工同步的列表。删除智能体可能照抄的旧做法和死代码。
2. **用类型强制约束，让错误状态无法写出来。** 如果错误代码仍能编译，就增加 lint 或 CI 检查，并在错误消息中指明应改用的文件、类型或函数。如果这一模式已经普遍存在，只在改动新增此类用法时让检查失败。
3. **测试行为。** 如果某项测试在其检查的行为损坏后仍然通过，或仅因内部实现变化就失败，修复或删除它。
4. **最后才写文档或智能体规则，且只用于需要判断的情况。** 智能体跳过文档时，没有任何检查会因此失败。

<a id="fix-and-prove"></a>

## 修复并证明

然后立即修复最常见的类别，每类一个提交。证明每个新检查都能在真实的历史错误上失败。本地和 CI 运行相同命令。例外必须写在违规行上，附上理由、到期日期和人工批准。

<a id="keep-the-rule-table"></a>

## 维护规则表

最后，在智能体指令文件中维护一张表，将每条规则与强制执行它的机制对应起来。操作者纠正你时，修复错误并增加规则。如果规则早已存在，却没有任何机制执行它，这就是再次发生的错误；在同一次改动中，从能够奏效的最高层级修复。某种错误不再可能发生后，移除相应规则。

**回复：**列出每类错误及其证据、你选择的层级，以及更高层级为何不适用。
