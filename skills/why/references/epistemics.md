# 认知与置信框架

当证据来自历史、零散且有时相互矛盾时，如何判断置信程度，以及如何向用户说明而不将其压平成虚假确定性。代码展示它做什么，并不展示*为什么存在*。原因藏在提交、PR、工单、文档和会话中；这些记录都不完整、存在偏差，而且有时缺失。假装并非如此，只会产生听来笃定却误导用户的猜测。

<a id="confidence-tiers"></a>
## 置信等级

输出中的每项主张都必须归入一个等级。等级决定其所在章节和措辞。

<a id="1-direct"></a>
### 1. 直接证据

明确的文字引用回答了问题：作者实际*写下*了说明原因的内容，而不是“代码做 X，所以作者必定想要 X”。例如，PR 描述“这修复了用户拥有 >1000 个条目时无法分页的缺陷”，工单“我们添加此功能，是因为客户 Acme 在安全审查中提出了要求”，代码注释“// 限制为 100，因为上游 API 拒绝更大的值”，设计文档“选择方案 A 而非 B，因为需要在重启之间持久保存”，或作者的聊天消息“改用这种方式，因为旧方案在测试中不稳定”。

措辞：肯定、现在时、附引用。“它存在，是因为 X。”

<a id="2-supported"></a>
### 2. 证据支持

多条间接证据汇聚到一个结论。没有任何单一来源明确说明，但跨来源的模式使其很可能成立。例如，PR 标题写着“改进性能”，工单标有 `perf`，周边提交都触及同一热路径；或者改动新增的多个测试都使用非常大的输入；或者作者同一周的其他 PR 都提到同一事故。

措辞：有信心，但明确说明是推导而来，并引用每项证据。“证据强烈指向 X：[具体证据]。”

<a id="3-inferred"></a>
### 3. 推断

对上下文作出的合理解读，但没有明确证据支持。它是*你的解释*，而非记录中的事实。例如，PR 没有说明原因，但错误当时正在生产环境发生（依据事故频道的时间），而修复十分仓促（同一天合并），因此它很可能是紧急修复。或者函数名暗示重试逻辑，而其重试次数 3 与代码库其他位置团队采用的 3 次重试惯例一致。

措辞：保留余地，并明确推理链。“考虑到 A 和 B，C 看起来很可能，因为 D。”

<a id="4-speculative"></a>
### 4. 猜测

证据薄弱时的合理假设，其他解释同样说得通。值得呈现，因为用户也许知道哪一个正确，但要标为猜测。例如，“这可能是针对一个后来已修复的浏览器缺陷的绕行方案，但我们没有找到当时的证据”，或“这个阈值可能是为了匹配 SLA 承诺，但没有 SLA 文档提到它。”

措辞：“一种可能是 X，但我们没有直接证据。”通常放在“竞争假设”中，与其他可能性并列。

<a id="5-unknown"></a>
### 5. 未知

你查找过，但未能弄清。这是有效且重要的结果，应记录下来。

措辞：“我们搜索了 X、Y、Z，没有找到说明原因的证据。”具体说明搜索了*什么*。“我们没能查明”不如以下表述有用：“我们使用关键词 A 和 B 搜索了工单系统，扫描了自 2023 年以来触及此文件的 6 个 PR，并在仓库中搜索了与阈值匹配的字符串字面量。均未发现依据。”

<a id="phrasing-guide"></a>
## 措辞指南

**肯定措辞**暗示直接证据或证据支持，必须在紧邻位置附上引用。绝不能用于推断：“因为”“原因是”“设计目的是”（声称作者意图）、“修复／处理／解决”（声称改动达成了目标）、“团队决定”（声称曾发生集体决策）。

**保留措辞**表示解释，而不是事实报告。在“合理推断”中充分使用：“看起来”“似乎”“很可能”“暗示”“与……一致”“一种解读是”“有可能”“可能曾经”“证据指向”。

**应避免的词语：**

- “显然”。如果显然，用户就不会问。
- “明显”。它几乎总是出现在并不明显的主张之前。
- “当然”。同上。
- “只是”（如“它只是为了性能而做 X”）。轻慢，且通常掩盖不确定性。
- “我认为／我相信”。你是在综合证据，不是发表个人观点。改用“证据提示”。

<a id="avoid-rationalization"></a>
## 避免事后合理化

今天“说得通”的代码，可能是出于如今已不适用、甚至当时就错误的原因而编写的。不要给混乱历史事后套上一个整齐的理由。不要假设作者做了“正确”的事，再倒推理由。不要假设一致模式一定是有意设计，它也许只是复制粘贴。不要将缺少证据变成不存在的证据（“没人提过安全顾虑，所以这一定不曾是顾虑”）。

<a id="the-sycophancy-trap"></a>
## 迎合陷阱

用户常在问题中嵌入假设：“我们为什么这么做，我猜是为了性能？”不要直接确认。这个猜测是调查的起点，不是待验证通过的结论。将其与其他候选假设一视同仁，独立检查证据。如果证据支持，用引用说明；如果不支持，也应说明，并呈现证据*实际*支持的内容。

<a id="when-evidence-contradicts"></a>
## 证据冲突时

在输出中展示双方来源，并附引用。不要选择更符合整齐叙事的那个。例如，工单写“这是为了客户 X 的合规要求”，PR 写“清理这一区域的技术债”。两者可能都对（工单推动工作，PR 提供作者的表述视角），也可能有一方错误。让用户判断。

<a id="when-evidence-is-missing"></a>
## 证据缺失时

诚实的“我们不知道”是最有价值的输出之一。用户得知答案不在明显位置，需要询问某个人（原作者、产品负责人、团队负责人），或可以决定不值得继续追查。如果不标明缺口，而用笃定的猜测填补，会直接伤害用户，因为他们会依据猜测行动。具体说明每项缺口：问题是什么、搜索了哪些来源、在各来源中搜索了什么、发现了什么（没有，或只有间接相关材料）。

<a id="before-finalizing"></a>
## 最终交付前

综合者交付输出前，检查“发现的事实”和“合理推断”中的每一项主张。每项主张要么有引用，要么移至“推断”或“假设”。措辞须与等级一致。不能将代码视为其自身意图的证据（若有，删除或重新分类）。输出必须有“尚不清楚的内容”章节。如果没有提到缺口，就值得怀疑：要么证据异常完整，要么某些内容被掩盖了。
