# Linear 工单

<a id="what-this-source-contains"></a>
## 此来源包含什么

- 描述功能、缺陷及其动机的工单
- 附在工单上的项目文档（通常为 PRD 或规格）
- 父工单／子工单关系（更大范围的计划 → 具体工单）
- 工单评论（澄清、范围变化、“为何做此事”的依据）
- 提示动机类型的标签（例如 `compliance`、`customer-request`、`perf`）
- 解释范围变化的状态更新
- 附件及关联的 GitHub PR

产品／业务背景常在 Linear 中：即“因为客户 X 要求，所以我们做这件事”或“这是 Q3 合规计划的一部分”这一层。

<a id="how-to-search-it"></a>
## 如何搜索

使用 Linear MCP。

1. **从关联工单开始。** 如果种子提交或 PR 引用了工单 ID（如 `ENG-1234`、`[BUG-567]`），先用 `get_issue` 获取它们。阅读完整工单，包括评论。
2. **按关键词列出相关工单。** 使用 `list_issues` 对功能名、关键符号或业务术语进行文本搜索。尝试多种措辞。
3. **沿工单树追踪。** 如果找到子工单，获取其父工单。子工单偏执行层面，父工单常包含“为什么”。
4. **阅读项目文档。** 如果工单属于某个项目，使用 `get_project` 检查所附文档。规格和依据最常记录在项目层级文档中。
5. **检查标签和里程碑。** 标签暗示动机类别（customer-request、incident-followup、compliance）。里程碑将工作与截止时间关联，常能揭示动机。

<a id="what-good-evidence-looks-like-here"></a>
## 此处的优质证据

- 陈述业务问题的工单描述：“客户 Acme 因 SOC2 审计需要 X”
- 记录决策的评论：“我们决定采用方案 B，因为方案 A 需要改动计费服务”
- 标题类似计划的父工单：“Q3 企业级准备”或“减少支付失败”
- 附带的 PRD 或规格
- `customer:acme`、`incident-followup`、`compliance`、`perf-regression` 等标签

<a id="common-pitfalls"></a>
## 常见陷阱

- **范围漂移。** PR 引用的工单可能已关闭，又以不同范围重新打开。阅读完整历史。
- **机械模板。** 有些团队要求填写“为什么”章节，却塞入套话。泛泛的文本（“改善用户体验”）很可能不是真正答案。
- **过期工单。** 旧工单常反映后来已变化的计划版本。检查日期，并与代码交付日期交叉核对。
- **以重复为由关闭的链条。** 沿重复关系追溯到规范工单。
- **私有工作区内容。** 无法访问工单时，记为缺口，不要猜测。

<a id="what-to-return"></a>
## 返回内容

对每个相关工单：
- 工单 ID 和标题
- 从描述或评论引用的问题／动机（不可转述；综合者需要原文来引用）
- 标签、父工单、项目
- 作者、创建日期、关闭日期
- 工单链接（如有）
