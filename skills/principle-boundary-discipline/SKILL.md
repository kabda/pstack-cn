# 边界纪律

把校验、类型收窄和错误处理放在系统边界。无条件信任内部代码。业务逻辑位于纯函数中，外壳保持轻薄、机械。

**原因：** 散落校验会带来噪声、冗余和虚假的安全感。让逻辑脱离框架接线，才能不依赖框架进行测试。

**做法：**
- **边界处**，例如 CLI 参数、配置文件、外部 API、网络协议：校验、返回错误、防御性处理。
- **系统内部：** 使用类型化数据，传播错误，不重复校验。信任类型。
- **跨越边界。** 暴露领域概念，不暴露边界的私有表示。通用机制放在内部，专用策略放在边缘。

**应用：**

校验与错误处理：
- 在解析时，即边界处，校验配置，不在业务逻辑内部校验
- 在边界把原始数据解析成领域类型
- 不通过公开接口重新导出传输、存储、框架或线格式类型
- 边界已校验时，不在调用链深处重复检查 nil

代码组织：
- 业务逻辑放在没有框架依赖的纯函数中
- 解析函数是从原始字节到类型化状态的纯转换
- 提示词构造接受结构化状态，输出字符串
- 评分和评估是从状态到结果的纯转换

**判断问题：**
- “这份数据此刻正在跨越系统边界吗？”如果没有，校验就是冗余。
- “这能否成为外壳直接调用的纯函数？”如果能，就提取出来。
