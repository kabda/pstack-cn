# 先隔离，再串行化共享状态

并发参与者可能共享可变状态时，先问它们是否需要同一个可变对象。不需要就消除共享。确需共享时，用结构强制串行化，例如锁文件、顺序阶段、独占归属。指令和约定不是并发控制。

**原因：** 对共享状态的并发写入会产生间歇性、难复现且调试代价高的竞态条件。

**做法：**
1. **识别共享可变状态**，例如双方都读写的文件、都推送的分支、都定义并使用的 API。
2. **默认消除共享写入目标。** 问：这些参与者需要同一个权威对象，还是各自发布独立事实？给每个参与者自己拥有的文件、键、分支或状态目录，只在读取 / 报告边界合并。两个工作者向同一 `state.json` 写各自的 `lastX` 字段，仍然是共享修改。`indexer-state.json` + `metrics-state.json` 则不是。
3. **只有单一共享写入目标确为不变量时，才用结构串行化访问**，例如锁文件、顺序阶段、单写入者参与者、原子 compare-and-swap。把“需要一个锁”当成要检查的设计异味，而非默认答案。
