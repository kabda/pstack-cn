<a id="figure-it-out"></a>

# 自行找到解决办法

任务不符合任何操作手册时，就设计一份。在编写任何代码之前，首先交付工作流本身：一系列与任务相称的阶段，运用科学方法，并留下可供人离开后回来审计的决策轨迹。

<a id="start"></a>

## 开始

创建待办清单，第一项是阅读 **poteto-mode** 技能的“原则”部分。然后将下面各阶段加入待办事项。

<a id="phase-a-frame"></a>

## 阶段 A：界定任务

先以事实为基础，再作承诺。只有能说明以下内容，才开始执行：

- 以可证伪谓词定义完成条件（**prove-it-works** 原则技能）。
- 量化范围：大致工作单元与投入，以及事实核查发现的阻碍。
- 严谨程度，宁高勿低。不可逆决策和影响范围大的工作需要更高严谨程度；可逆、低风险步骤则较低。严谨程度体现为门禁和产物，而不是“更加努力”。

承诺长时间执行前，先展示任务界定和取舍。可逆工作继续推进（**never-block-on-the-human** 原则技能），但持续数小时的执行值得安排一次检查点。

<a id="phase-b-design-the-workflow"></a>

## 阶段 B：设计工作流

拆分成原子化、可独立落地的单元。优先处理风险最高的未知项。脚手架和验证先于功能（**foundational-thinking** 原则技能）。

- 在实际工作前建立验证运行环境，先捕获改动前状态作为基线，让检查直接呈现“旧值与新值”的对比。
- 遇到不可逆的设计决策，运行 **architect** 技能（它会运行 **arena**）。对于形态已经明确的机械性工作，跳过它。设计已经确定后再运行一次 arena，属于过度工程（**laziness-protocol** 原则技能）。
- 决定哪些工作可以展开并行。只沿明确边界并行，为每个工作者提供独立的 Git 工作树或分支（**separate-before-serializing-shared-state** 原则技能）。不要过度拆出并行任务。根据 **poteto-mode** 技能的“子代理”部分，为每个子代理选择适合任务的推理级别以及快速或标准速度。
- 写下设计好的阶段列表。这份列表就是供人审查的内容。

然后执行设计。把具体步骤作为待办事项插入阶段 C 和阶段 D 之间。每一步都遵循阶段 C 的循环纪律，同时贯穿阶段 D 的日志记录：每个步骤落地就记一行，而不是到最后才补写全部轨迹。

<a id="phase-c-run-the-loop"></a>

## 阶段 C：运行循环

每个单元都是一次实验。提出假设，做最小改动，在真实产物上依据谓词测量；有推进则保留，没有则回退。应用 **sequence-verifiable-units** 原则技能，在开始下一个单元前验证当前单元，不要把检查集中到最后。

- 通过检查产物来验证，绝不能依赖自我报告。通过得过于容易时，先怀疑观察方法，再怀疑系统。
- 为委派的工作配备评判者。如果工作者投机绕过门禁，重置并强化约定。如果门禁本身有误，单独修复门禁，不要绕开它。
- 结论只能是 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE。无法得出结论不等于通过。不要隐瞒负面结果。

<a id="phase-d-keep-the-audit-trail"></a>

## 阶段 D：保留审计轨迹

通过 **show-me-your-work** 技能记录执行。figure-it-out 的工作通常足够复杂，应当把轨迹提交到仓库，让审查者能在 PR 中阅读。轨迹和 diff 共同使人能够回来后信任这些工作。

<a id="phase-e-verify-and-hand-back"></a>

## 阶段 E：验证并交回

依据阶段 A 的谓词检查真实产品整体，而不仅是验证运行环境。把反复出现的纠正编码为门禁、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：**你设计的操作手册、严谨程度及原因、决策轨迹路径、已经按谓词验证的内容，以及尚未解决的事项。
