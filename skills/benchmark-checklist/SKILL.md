<a id="benchmark-checklist"></a>

# 基准测量检查表

产生性能数值时使用：PR 的改动前后对比、性能退化结论、爬坡优化运行环境，或库与配置的选择。每个问题都要用实际运行的证据回答，不能猜测代码会怎样。

如果用户只要求快速估算，运行一次即可。仍需检查问题 4 和 7，并说明只有一次运行。除非这次结果看起来不对，否则跳过其他问题。在选项之间作选择，绝不属于粗略估算。

<a id="before-you-run-anything"></a>

## 运行前

- 写下预计要作出的结论，直接采用准备交付的表述（“在 60k 行数据集上，导出 p50 快了 30%”）。下面的问题就是用来检验这句话的。
- 阅读测量脚本，记录它计时、计数和忽略的内容。
- 用 `uptime` 检查平均负载，用 `nproc` 检查核心数。如果机器繁忙，查明正在运行什么。如果不能停止，就交错运行两侧，让它们受到相同噪声影响，并在报告中说明。

<a id="the-questions"></a>

## 检查问题

1. **为什么不能再快一倍？** 指出限制因素。性能分析器和追踪器会拖慢工作，因此在不纳入报告的单独运行中分析。使用进程 CPU（`top`、`pidstat`）、运行时性能分析器（`node --cpu-prof`、`py-spy`、`perf`）、I/O 等待和系统调用计数（Linux 的 `strace -c`），然后把热点对应到源码。也要监控负载生成器：如果它先饱和，你测到的就是负载生成器。如果改动没有影响数值，限制因素会解释原因；在称改动无用前先找出它。
2. **是否调优？** 两侧都按生产运行方式执行：release 构建、生产参数和环境变量、批处理与事务设置、连接池、与生产相同的冷暖缓存，以及相同版本和数据。如果一侧使用默认值，你比较的是配置，而非实现。若限制因素来自设置（每行一次提交、debug 构建、缺少索引），说明这一侧尚未调优。先调优、重测，再选胜者。如果无法调优，就不要根据这次运行选出胜者。用户正在选择采用哪个方案时，把结论缩小为当前交付代码也无法解决这个问题，因为他们采用的是方案，不是今天的设置。
3. **是否突破极限？** 做算术核对。把每秒字节数与磁盘及网络带宽比较，把每秒操作数乘以单次成本与核心数比较，把节省时间与被修改部分原先耗时比较。移除占运行时间 10% 的部分，最多只能使运行速度提高约 11%。超过极限的结果测到的是别的东西，例如缓存、空操作或缺陷。
4. **是否出错？** 统计失败与非成功响应，并检查输出正确，而不仅是存在。拒绝请求通常很快，超时和重试则很慢。如果脚本没有统计错误，就加入统计。
5. **能否复现？** 每侧至少运行 5 次，交替进行（A、B、A、B，依此类推），使预热、延迟初始化、缓存和漂移都不偏向某一侧。报告中位数与范围。差距小于各次运行的波动，就没有可测差异。结果接近时，使用秩和检验或运行环境自身的统计方法。
6. **是否有实际意义？** 除微观结果外，还要以真实数据规模和并发量测量用户等待的端到端路径，并报告微观结果占整体的比例。一个辅助函数占请求时间 1%，无论它变得多快，最多也只能使请求快 1%。
7. **工作真的发生了吗？** 确认工作发生在计时区域内：请求到达服务器，行已写入，字节已读取，代码使用了结果。惰性代码（无人迭代的生成器、无人等待的 promise、可被 JIT 丢弃的结果）和超时会为从未发生的工作产生数值。

<a id="report"></a>

## 报告

- 先给结论：更快、更慢、无可测差异，或无法得出结论。
- 给出数值、单位、运行次数、范围和限制因素。例如：“p50 41 ms → 33 ms，每侧 7 次运行的中位数，改动后范围 32 至 35 ms，受单核 JSON 解析限制。”
- 声称存在差异却说不出限制因素、一侧未调优，或未能检查问题 4 和 7 时，结论必须是无法得出结论。写明缺口。
- 根据 **创建拉取请求（Opening a PR）** 操作手册，PR 正文只保留一个主要数值。具体运行、范围和限制因素证据放在链接的产物或笔记文件中。

<a id="other-perf-material"></a>

## 其他性能材料

- **性能问题（Perf issue）** 操作手册依据基线作计划前，先核查基线；之后每个数值也都要核查。
- **爬坡优化（Hillclimb）** 操作手册冻结运行环境前先核查它。冻结后的运行环境会打印错误和工作计数，因此每次保留或回退时，都能顺带检查问题 4 和 7。
