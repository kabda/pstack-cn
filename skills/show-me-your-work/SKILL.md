<a id="show-me-your-work"></a>

# 展示工作轨迹

只保留一份权威日志。

<a id="the-format"></a>

## 格式

单个 TSV 文件，每个决策一行。每个单元格只占一行。证据是指针，不是正文。

复制 `references/decision-log-template.tsv` 的表头行，开始干净日志。各列：

- **ts。** ISO8601 时间戳。
- **phase。** 阶段或工作流。
- **decision。** 选择或做了什么，一行。
- **why。** 用通俗语言说明理由。由原则驱动时直接解释，不用术语标签。
- **evidence。** 能证明它的链接或路径：commit SHA、PR 编号、`file:line`，或产物、追踪、截图路径。绝不是段落。
- **result。** 结果或谓词状态：`tests green`（测试通过）、`reverted`（已回退）、`pixel-diff 0`（像素差为零）、`INCONCLUSIVE`（无法得出结论）、`open`（未解决）。

下面是通俗示例，让审查者一眼能读懂。

```
ts	phase	decision	why	evidence	result
2026-05-24T09:02:00Z	frame	先清点工作量，约 100 个组件、75 小时	开始长期运行前先了解规模	commit 3a9f1c2	发现开始前需理清的 5 个问题
2026-05-24T09:40:00Z	harness	修改前给旧版本截图	比较新旧并捕获任何视觉变化	scripts/snapshot.sh, baseline/	保存了 120 张参考截图
2026-05-24T11:15:00Z	widget	迁移组件样式，外观不变	保持改动小且结果相同	commit 7c21e0a, pixel-diff 0	外观相同，测试通过
2026-05-24T12:30:00Z	widget	辅助代理的截图为空，因此丢弃其工作	检查实际文件，不相信摘要	worktree reset	已回退，收紧下一次的指令
```

<a id="logging-a-row"></a>

## 记录一行

像告诉队友做了什么一样写每条记录。用平实词语和具体动作，不用 AI 腔或抽象术语（**unslop** 也适用于日志文字）。

使用辅助工具 `scripts/log.sh <logfile> <phase> <decision> <why> <evidence> <result>`。它填入 `ts`，首次使用时写表头，移除多余 Tab 和换行，并为任何以 `=`、`+`、`-`、`@` 开头的单元格加前置单引号。直接用 `printf` 追加一行也可以，但生成文本或用户文本同样要注意这些字节。

记录决策点与检查点，而非每个动作：选定分支路线、单元完成及验证结果、转向或回退及其触发原因、发现阻碍、修复门禁。循环执行每轮一行。跳过琐碎和不言自明内容。

一次运行指一个智能体对话，包括后续回合和任何摘要。接续、替换智能体或新聊天都开始新运行。某运行向已有行的日志追加时，首行 phase 为 `start`；若另一次运行写入 `start` 行，本运行之后第一次继续写入也要先写 `start`。因此后续回合返回日志时，先读末尾几行，判断期间是否有其他运行写入。`start` 行指出在它之前、本运行没有写入的行的 `ts` 范围，evidence 则标识本运行，例如智能体 ID。phase `start` 不作其他用途。

<a id="where-it-lives"></a>

## 存放位置

默认日志是工作产物，不提交。放在工作目录的 `decisions.tsv`，多个工作同时进行时放在 `.audit/<task-slug>.tsv`，不纳入 Git。

只有工作足够复杂、审查者需要轨迹才能信任结果时，才提交。

<a id="rules"></a>

## 规则

- 只追加。错误决策用新行取代，绝不编辑或删除历史。
- 优先采用已提交脚本产生的证据，而非手工一次性操作（**encode-lessons-in-structure** 原则技能）。

<a id="audit-the-log-against-the-transcript"></a>

## 对照对话记录审计日志

运行结束、交回前，检查日志是否真实。从当前工作区会话目录读取本次记录：Cursor 为系统提示词指定的 `agent-transcripts/`；Claude Code 为 `~/.claude/projects/<slug>/`（工作区路径所有非字母数字字符换成“-”）；Pi 为 `~/.pi/agent/sessions/--<slug>--/`；Codex 为 `~/.codex/sessions/` 中首行 `payload.cwd` 等于工作区路径的文件。不要跨每个项目目录搜索，那会读取无关私人聊天。逐段对照本运行的行与实际发生的事。每段始于本运行某个 `start` 行；如果日志由本运行创建，则也可从首行开始；段落在另一次运行的下一个 `start` 行前结束：

- 每行都必须对应真实决策或动作。
- 每行证据都能解析到内容，并支持其说法。
- 影响了工作的路线选择、转向或放弃方案若未记录，就是缺口，补上。

纠正日志，不要改写故事。审计绝不编辑或删除行，即使是虚构行。如果某行既非真实决策也非真实动作，或说法、证据有误，增加新行，以实际发生的事和可解析指针取代它。此次审计不检查本运行各段之外的行；但本运行自己的工作若证明其中某行有误，也像其他错误决策一样用新行取代。

<a id="cross-model-review-of-the-trail"></a>

## 对轨迹进行跨模型审查

交回前，启动一个与实际工作模型不同系列的子代理。自审不能替代它。子代理阅读审计轨迹和本次对话记录，指出用户应注意的内容。这不是重做工作，而是扫描不理想或有风险的部分。根据 **poteto-mode** 技能的“子代理”部分，为每个子代理选择适合任务的推理级别以及快速或标准速度。

- 记录的决策证据薄弱或缺失。
- 跳过的验证，或记录中没有证明却声称完成的验证。
- 事后看存在风险的选择（过早决策、扩大范围、掩盖症状）。
- 用户粗略浏览时会漏掉的缺口。

产生轨迹的运行，每次回复都以 “Attention”（注意事项）部分结束。先单独一行写审查者模型（`reviewed by <model>`），然后列出每项标记，指向具体行或时刻。“No flags”（无标记）是有效结果，模型名称本身不是结果。

<a id="reviewing-the-trail"></a>

## 审阅轨迹

从上到下阅读，沿证据指针抽查。GitHub 会把已提交 TSV 渲染为表格。终端可用 `column -s$'\t' -t decisions.tsv` 渲染。

<a id="composing-this-skill"></a>

## 组合使用本技能

其他技能将审计轨迹交给本技能，不再发明另一套。按名称引用，让它负责格式，不重述列定义。
