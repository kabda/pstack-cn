<a id="arena"></a>

# 竞技场

启动任何工作前，建立每阶段一项的待办清单（界定任务、展开并行、交叉评判、选择、移植、验证）。

<a id="phase-a-frame"></a>

## 阶段 A：界定任务

每个候选方案获得同一份提示词，因此提示词就是约定。

1. 说明每个候选方案要产出的产物。
2. 制定评分标准，用 3–6 项具体、可评分的条件说明*这项*任务怎样才算成功。这是阶段 D 选择者的工具；候选方案只看到任务。
3. 选择执行者。使用 pstack 设置文件的 `arena runners` 行（Cursor 为 `~/.cursor/rules/pstack-models.mdc`，Claude Code 为 `~/.claude/rules/pstack-models.md`，其他智能体运行环境为 `~/.agents/pstack-models.md`）。文件或该行缺失时，默认分别使用一个 `claude-opus-5-5-xhigh` 和一个 `grok-4.7-xhigh-fast`。该行的 `auto` 或 `inherit-parent` 条目代表父模型，因此省略其 `model`。如果子代理工具拒绝某个配置条目，该席位改用所属系列的默认模型，并说明。系列按前缀划分：`claude-*` 是一组，`grok-*` 与 `cursor-grok-*`、`composer-*` 是一组。其他前缀（如 `gpt-*`）各自为一组。被拒绝的 `composer-*` 条目改用 `grok-4.7-xhigh-fast`。如果系列没有默认值，或子代理工具拒绝该默认值，从错误消息或运行环境模型列表中选同系列最接近的有效 slug；没有可选项时取消该席位并说明。如果取消后不足两个执行者，就补至两个；但该行本来只有一个条目时，补至一个即可。新增执行者使用剩余执行者的模型；若一个都不剩，则省略 `model` 以使用父模型，并说明。竞技场覆盖多个设计方向时，启动更多执行者。工作主要受生成量而非判断质量限制时，可让同一模型运行 N 次。根据 **poteto-mode** 技能的“子代理”部分，为每个子代理选择适合任务的推理级别以及快速或标准速度。
4. 根据 **separate-before-serializing-shared-state** 原则技能，为每个候选方案提供独立输出位置（尽可能使用 Git 工作树，否则为 `/tmp/arena-<slug>/candidate-<n>/`）。

<a id="phase-b-fan-out"></a>

## 阶段 B：展开并行

在一条消息中启动全部 N 个子代理，设 `run_in_background: true`。分别提供任务、共享事实基础的路径、各自输出路径，以及要求：产出目标产物，附上简短理由，说明考虑过哪些替代方案、拒绝了什么。

某个候选方案没有输出时，以 N-1 个方案继续，并注明退出情况。

<a id="phase-c-cross-judge"></a>

## 阶段 C：交叉评判

阶段 B 所有候选方案完成后，从 pstack 设置文件的 `arena cross-judge pool` 行选择一个模型。文件或该行缺失时，从 `claude-opus-5-5-xhigh` 和 `grok-4.7-xhigh-fast` 中选择。启动一个只读评判子代理。按阶段 A 第 3 步定义的系列，评判者绝不能来自父模型的系列。按池中顺序，仅尝试其他系列的条目。`auto` 或 `inherit-parent` 条目代表父模型，因此绝不担任评判。使用默认池时，Claude 父模型选择 `grok-4.7-xhigh-fast`；其他系列的父模型先选 `claude-opus-5-5-xhigh`。如果子代理工具拒绝某条目，从错误消息或运行环境模型列表中，选择同一模型最接近推理级别或速度的有效 slug；没有则试下一条目。如果其他系列的所有条目均无法运行，用同样方法尝试默认池的其他系列条目。如果仍无可运行项，就跳过评判，在阶段 D 独自选择基础方案，并说明。如果不知道父模型是什么，按池顺序尝试真实 slug，并说明未执行系列检查。评判者看到评分标准和按路径标记的候选方案，逐项评分，推荐基础方案并说明理由。它与你在阶段 D 的阅读并行进行。候选方案仍在写入时，不要启动评判者。

<a id="phase-d-pick-a-base"></a>

## 阶段 D：选择基础方案

选择前从头到尾阅读每个候选方案。逐项依据评分标准评分，而不是凭整体感觉；阶段 C 运行了交叉评判时，与其结果比较。对基础方案达成一致，可以确认选择；有分歧意味着其中一方有偏见，或评分标准含糊。决定前先阅读双方理由。

选择未来维护者最容易扩展且不会破坏不变量的方案。两者相当时，按惰性协议（Laziness Protocol），优先选择边界更清晰或 API 更小的方案。

<a id="phase-e-graft"></a>

## 阶段 E：移植优点

再遍历每个落选方案一次，寻找值得移入基础方案的内容；每个通常一两处，而非大半方案。根据 **redesign-from-first-principles** 原则技能，手动整合每次移植，让结果在同一心智模型下保持一致。不要机械粘贴。

如果候选方案收敛到同一种结构，说明一致性很强。记录这一点，交付共识结构，无需移植。如果方案差异极大，说明阶段 A 定义不足。重新界定并重跑，不要把分歧取平均。

<a id="phase-f-verify"></a>

## 阶段 F：验证

按 **prove-it-works** 原则技能，像验证其他输出一样验证综合产物。如果验证发现竞技场遗漏的问题，要么阶段 A 有误（重新界定并重跑），要么某个候选方案已经捕获问题但移植时漏掉了（回到阶段 E）。不要掩盖。

<a id="outputs"></a>

## 输出

一个综合产物，随附简短综合说明：指出基础方案及原因、交叉评判结论或阶段 C 跳过评判的事实、每次移植及其来源、被拒绝内容及原因、是否出现收敛或退出，以及验证结果。
