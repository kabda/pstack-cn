# 领域建模

把真实领域编码进数据结构，不要散落在条件判断中。匹配领域的结构让非法状态无法表达，并删除分支。编写时选择它成本很低，日后补回会被视为重构而延期。

可考虑：

- 状态机，替代散落布尔值、阶段或生命周期检查。
- 类型化模型，替代松散参数或重复形态假设。
- map、注册表、查找表或判别联合，替代跨文件散落分支。
- reducer 或命令 / 事件模型，替代临时状态修改。
- 围绕一组领域知识组织的模块，替代加载、校验、转换、保存这样的步骤序列。执行顺序不等于归属。
- 汇集重复行为、归属或不变量的小模块边界。
- 访问模式适用时，使用队列、缓存、索引、图、树或规范化集合。
- 任何其他合适结构。没有合适结构时，先弄清代码绝不能允许什么，以及数据如何读取，再找到准确编码这些要求的结构。

不要强加抽象。当前形态已清楚、局部且不太会增长时，优先朴素代码。对只增加间接层，却不删除分支、重复规则、非法状态或生命周期风险的抽象保持怀疑。

跳过本原则的迹象包括：新功能只给已有 if/else 链加一个分支，或新增第二个必须与第一个同步的布尔值。按时间分解也是迹象，以阶段命名的模块会在步骤间重复同一领域规则。
