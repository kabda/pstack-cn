<a id="maintain-a-formal-verification-skill"></a>

# 维护形式化验证技能

形式化检查证明的是它所描述内容的性质。代码改变而验证未变时，检查可能一直通过，却描述着已不存在的代码。这种通过最危险，因为看起来像证明。本技能维护 `/create-formal-verification-skill` 生成的验证技能，或任何针对指定代码运行模型检查器、证明器或代码级验证器的项目本地技能。项目本地技能负责智能体在使用该技能时所作的改动；本技能处理那些跳过验证的变化：合并、不使用技能的编辑，以及多个提交积累的漂移。

<a id="outcomes"></a>

## 结果

为每项检查给出并说明一种结果：

- **in sync**：上次同步以来没有改动影响检查所描述的内容，且检查通过。
- **updated**：代码改变，验证现在准确描述新代码，且检查通过。
- **bug**：验证准确描述当前代码，而代码违背性质。这是代码问题，不是漂移。
- **blocked**：无法重新对齐检查，或无法运行。准确说明原因。

一项检查可以同时是 updated 和 bug：更新使验证重新描述代码，随后性质在该代码上失败。

<a id="edit-scope"></a>

## 编辑范围

只编辑验证内容：模型、运行工具、性质文件和验证技能本身。除非用户要求，否则执行期间绝不编辑产品代码。性质在当前代码上失败时，不要削弱性质或模型来使其通过；报告失败。

<a id="pass"></a>

## 执行流程

1. **找到检查。** 验证技能没有固定名称，按行为寻找：对指定代码运行模型检查器、证明器或其他验证器的项目技能。阅读所有找到的技能，或用户指定的技能。对每项检查收集性质、覆盖代码、边界与假设、运行命令，以及上次确认准确描述代码的 commit。没有验证技能时，停止并指向 `/create-formal-verification-skill`。技能未记录同步 commit 时，采用最后修改验证文件的 commit，并说明这一做法。

2. **按原样运行。** 修改任何内容前，每项检查运行一次并记录结果。此时通过并不说明代码正确，只说明旧描述仍成立。失败可能是漂移或缺陷，第 5 步之前不作定论。

3. **阅读受覆盖代码的每项改动。** 对覆盖文件比较同步 commit 与当前 commit 的 diff，阅读每条提交消息。也要寻找移动的代码：受覆盖函数重命名、拆分或移到其他文件后，仍属覆盖范围。还要找触及检查所保护状态的新代码，例如写入相同字段的新函数。逐项判断属于以下哪类：
   - **无影响。** 改动不改变验证描述的任何内容，例如格式、注释，或验证不覆盖的代码路径。必须对照模型或运行工具检查，不能只看提交消息。
   - **验证已不再描述代码。** 原先不可分割的一步变成两步、新增或移除分支、检查移动、新路径到达受保护状态，或值域改变。模型或运行工具必须变化。
   - **承诺有意改变。** 改动改变代码承诺，且有证据说明这是有意的：文档注释、测试、变更日志或提交消息。性质必须改变，并引用该证据。
   - **承诺可能被破坏。** 代码改变，却没有证据表明承诺改变。将后续失败视为缺陷候选。

4. **按代码更新，不按结果更新。** 修改模型或运行工具，使每个变化部分重新指向审查者能打开的代码，并保持代码中一个不可分割步骤在验证中也是一步。先按代码写好更新，再重跑；不要为了使检查通过而塑造验证。只有承诺有意改变时才修改性质，记录旧表述、新表述和证据。保留边界，除非代码变化使其不再正确。若必须缩小边界，在报告中说明。

5. **重跑并判断每项结果。**
   - **通过：** 检查可能因为描述失去了失败能力而通过。按性质防范的方式破坏新代码，例如移除新检查或重排新步骤，确认检查能捕获它，然后丢弃破坏。
   - **失败：** 对真实代码逐步重放反例。如果某步不可能在代码发生，验证有误；修复验证并说明错误。如果每步都可能发生，就是缺陷。指出引入它的 commit，用代码自身的说法讲述反例步骤，并用一句话说明危害。如果低成本测试或对真实代码的复现能显示缺陷，把它作为证据加入报告，不要提交到产品代码。

6. **更新验证技能。** 更新每项检查覆盖的代码、命令、边界、假设和同步 commit。同步 commit 设为你检查过的 commit。blocked 检查不推进同步 commit，并在报告说明。然后像下一个智能体那样执行一次验证技能，确认步骤仍能运行。

<a id="report"></a>

## 报告

逐项告诉用户：

- 结果，以及阅读过的提交；
- 验证改了什么、为什么，每项变化简要归因：代码结构变化，或承诺有意改变（附证据）；
- 重跑结果，以及用什么破坏证明更新后的检查仍能失败；
- 通俗描述每个缺陷：用代码中的说法列出反例步骤、危害、引入 commit；
- 验证仍未覆盖什么，包括应覆盖而未覆盖的新代码。

明确说明哪些失败是验证漂移，哪些是代码缺陷。检查更新前通过、更新后失败时，说明旧的通过建立在过时描述上。

验证更新应独立成一次改动，与任何产品修复分开。
