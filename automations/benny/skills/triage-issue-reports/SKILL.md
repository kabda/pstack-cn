<a id="triage-issue-reports"></a>
# 问题报告分诊

对一条 Slack 报告分类，并在其来源线程中发布一个有用的结论。仅为明确的新缺陷创建跟踪工单。不要在这里复现或修复问题。

加载自动化提供的外部 Benny 配置。如果配置缺失、格式错误或不完整，应停止，不发消息，也不写入跟踪系统。

<a id="hard-safety-rules"></a>
## 硬性安全规则

- 来源频道和根线程坐标不可变。
- 绝不在来源频道发布根消息。
- 绝不向其他频道发消息、广播回复、发送私信或新建替代线程。
- 任何跟踪系统写入之前，以及发布结论前一刻，都要预检来源父消息。
- 如果父消息缺失、已删除、无法访问或情况不确定，应停止，不进行任何写入。
- 发布一次有实质内容的结论。不要叙述进度。
- 协调者是唯一的 Slack 发消息者。
- 受委派的工作者只返回发现。它们必须只读，不能获得 Slack 凭据或写入操作。
- 每个子代理提示词必须禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及其他一切 Slack 写入。
- 如果工作者隔离无法强制实施这些限制，就在协调者中完成工作。
- 绝不创建无法链接回来源线程的工单。
- 宁可不建工单，也不要创建靠猜测或重复的工单。
- 将 pstack 的 `principle-separate-before-serializing-shared-state` 应用于来源坐标。
- 将 pstack 的 `principle-minimize-reader-load` 和 `unslop` 技能应用于最终结论。

<a id="1-freeze-source-coordinates"></a>
## 1. 固定来源坐标

在制定工作列表或委派之前：

1. 从触发器读取 `source_channel_id`。
2. 要求它与配置的来源频道一致。
3. 如果存在 `trigger.thread_ts`，将其赋给 `SOURCE_THREAD_TS`；否则使用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 将 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 保存为不可变值。
6. 读取线程，验证根消息坐标与上述值完全一致。
7. 获取稳定的来源永久链接。

后续每次来源读取和发消息都必须使用这些保存值。绝不用回复时间戳或运维线程时间戳替换它们。

<a id="2-read-the-whole-report"></a>
## 2. 阅读完整报告

作决定前，读取根消息和当前回复。

记录：

- 报告者的措辞
- 已提供的产品版本、应用构建、环境和平台
- 预期行为
- 实际行为
- 出现频率和触发条件
- 错误文本或堆栈特征
- 现有工单、提交或拉取请求链接
- 明确说明已有人员正在修复的内容

检查每个相关附件。

- 以足够实用的完整分辨率阅读截图。
- 审阅视频，找出区分正确和错误行为的状态转换。
- 从日志、跟踪记录和崩溃文本中读取具体特征。
- 如果媒体需要专门审阅，使用只读媒体工作者，并提出范围明确的问题。工作者只返回发现。
- 如果附件无法读取，在结论中说明。不要臆造其展示内容。

向报告者索取更多信息前，先使用线程中已有的证据。

<a id="3-trace-cause-before-routing"></a>
## 3. 先追踪原因，再路由

选择负责人或去向前，对源代码和历史进行有明确边界的检查。使用 pstack 的 `how` 技能追踪从报告中的操作到实际结果的路径。当报告看起来是回归问题，或涉及防御性代码时，使用 `why`。

1. 识别从报告操作到实际结果的可能代码路径。
2. 检查可见症状属于该代码路径，还是其下层依赖。
3. 当报告看起来是回归问题时，检查近期改动。
4. 检查是否已有合并提交或开放的拉取请求处理同一症状。
5. 区分已确认事实和假设。

这轮检查无需得到完整根因，但必须足以避免将可见症状路由给错误的负责人。

如果无法读取仓库，不要猜测代码负责人。继续进行保守分类，并说明无法追踪原因。

<a id="4-classify"></a>
## 4. 分类

选择一个类别。

<a id="bug"></a>
### 缺陷

某种情况违反预期行为。例如错误输出、损坏状态、错误、崩溃、挂起、静默无操作或回归。

<a id="performance"></a>
### 性能

报告描述了可衡量的缓慢、内存过量、电池消耗、卡顿或其他资源问题。将其视为缺陷，但保留测量数据和性能分析记录。

<a id="feature-request"></a>
### 功能请求

当前行为看起来是有意设计的，而报告者希望得到不同的行为或操作方式。

<a id="question-or-feedback"></a>
### 问题或反馈

报告询问某项功能如何工作、表达偏好但未指出具体缺陷，或提供一般反馈。

<a id="reroute"></a>
### 转交

原因追踪表明，问题应由配置中的其他去向负责。

当缺陷与功能请求的界限不明确时，不要建工单。唯一一次结论可以提出一个聚焦的问题，并使用 `other` 标记。

<a id="5-apply-configured-routing"></a>
## 5. 应用配置的路由

从 `routing.map_path` 读取可选路由映射。

- 按已确认的产品区域、代码路径或错误特征匹配。
- 当原因追踪指向其他位置时，仅凭可见症状不足以路由。
- 如果没有匹配路由，说明负责人尚不明确。不要猜测。
- 不要跨频道转发。在来源线程中告诉报告者应将问题提交到哪里。

默认不 @ 负责人。只有以下条件全部成立时才允许 @：

1. 路由映射明确指定负责人。
2. 配置允许这种 @ 类型。
3. 该事项是需要负责人意见的功能请求，或近期历史以有力证据指出了可能引入回归的作者。
4. 负责人不是范围宽泛的值班组。

其他情形一律不 @。

<a id="6-use-the-issue-tracker-adapter"></a>
## 6. 使用问题跟踪系统适配器

跟踪系统是一个适配器，不要求使用特定供应商。Linear 适配器是一个有效示例。GitHub Issues 适配器或其他跟踪系统也可以实现同一契约。

配置的适配器必须提供：

- 按文本、状态、标签、来源 URL 和日期范围搜索工单
- 读取单个工单及其链接
- 创建包含标题、正文、状态、标签和来源 URL 的工单
- 更新已有工单而不替换无关字段
- 添加来源链接和再次发生说明
- 如果 Slack 交接失败，取消、关闭或删除本次运行创建的工单

如果某项必需操作不可用，应拒绝相应写入。

运行时解析配置的团队、项目、状态和标签。除非配置明确要求，否则不要编造 ID、创建标签、指派负责人或设置优先级。

<a id="7-dedupe"></a>
## 7. 去重

始终检查该来源永久链接是否已关联到跟踪工单或之前的分诊回复。若已关联，不要重复发消息或创建工单。

对于缺陷和性能报告，使用以下信息搜索跟踪系统：

- 精确的错误或崩溃特征
- 产品区域
- 触发条件
- 症状
- 版本或日期窗口
- 疑似引入回归的提交
- 来源永久链接

选择一个结果：

- 确信重复：特征相同，或区域、触发条件和症状相同，或已确认共同原因。
- 可能相关：共同原因看起来合理，但尚未证实。
- 相似性弱：只是表面相似。
- 无匹配。

对于确信重复的工单，更新现有工单，添加来源永久链接和一条简短的再次发生说明。除非配置要求，否则不要重新打开、更改标签或重新指派。

对于可能匹配的工单，在结论中链接并注明不确定，不创建任何工单。

一个关闭已久的工单是回归线索，并不自动算作仍有效的重复工单。

<a id="8-decide-whether-to-create"></a>
## 8. 决定是否创建

仅当以下条件全部成立时才创建：

1. 分类为缺陷或性能。
2. 行为明确存在问题。
3. 问题仍然存在，或尚不知是否已修复。
4. 去重没有找到确信或合理可能的有效匹配。
5. 来源父消息和永久链接通过预检。
6. 跟踪系统的目标字段已解析。
7. 如果结论发布失败，适配器能够补偿处理。

绝不为功能请求、问题、反馈、转交、可能重复、确信重复或已修复的问题创建工单。

新工单必须信息自足：

- 点明区域和症状的直白标题
- 报告者原话
- 预期和实际行为
- 版本和环境，或 `unknown`
- 触发条件和频率
- 来源线程永久链接
- 简短的原因追踪发现，将假设明确标为假设
- 支持时内嵌截图或有代表性的视频帧
- 其余产物的链接
- 配置的受理状态和标签

不要在标题中写猜测的根因。

<a id="9-post-one-verdict"></a>
## 9. 发布一次结论

重新预检来源父消息。然后使用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 恰好发布一次回复。

绝不在 `thread_ts` 非空这一条件不满足时调用来源频道的发消息操作。

回复保持简短：

- 先说结果。
- 如果有现有或新建的跟踪工单，附上链接。
- 必要时说明转交去向或一项缺失事实。
- 最多包含一次获准的负责人 @。
- 以恰好一行标记结束。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

仅使用配置的标记字符串。复现自动化只有在此来源线程中由配置的分诊身份发出标记时，才信任它。

发布后，读取同一来源线程，验证结论出现在 `SOURCE_THREAD_TS` 下。如果没有，绝不要在根层级重试。

如果本次运行创建了跟踪工单，但结论未成功发布，应使用适配器的补偿操作。验证工单已取消、关闭或删除。如果无法验证补偿结果，只在自动化运行输出中报告失败。

<a id="10-watch-one-follow-up-window"></a>
## 10. 观察一个跟进窗口

在配置的跟进窗口内观察来源线程，然后停止。

- 仅回答直接向分诊身份提出的问题。
- 在安全时，将具体纠正内容应用于跟踪工单。
- 同一次运行中不要发出第二个标记。
- 不参与人工协调和旁支闲聊。
- 如果有人要求自动化停止，应提前停止。

不要将窗口延长超过一次。新报告应开始一次新运行。
