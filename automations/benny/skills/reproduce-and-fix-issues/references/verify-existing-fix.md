<a id="verify-an-existing-fix"></a>
# 验证现有修复

当开放的拉取请求或已合并提交有合理可能修复报告时，使用此模式。

现有产物负责修复。验证它。不要编辑它、编写竞争补丁或再打开一个拉取请求。

<a id="qualify-the-artifact"></a>
## 确认产物符合条件

必须有一个具体产物：

- 含有处理该症状的代码改动的开放拉取请求
- 已合并的拉取请求
- 代码及意图匹配的已合并提交

没有拉取请求或提交的线程声明、跟踪系统状态、分支名称或原因假设都不够。

存在多个产物时，选择来源线程或跟踪工单链接的那个。否则选择与受影响代码最匹配的产物，并说明原因。

<a id="protect-the-working-tree"></a>
## 保护工作树

仓库支持时，使用隔离的 Git 工作树或其他干净检出。不要覆盖用户改动。

记录：

- 基线修订版本
- 打补丁的修订版本
- 拉取请求或提交 URL
- 两次运行共用的构建及环境输入

使用普通 `github.com` 拉取请求链接。

<a id="measure-the-baseline"></a>
## 测量基线

对于开放的拉取请求，使用其基准分支作为基线。

对于已合并修复，在修复前一个版本能构建且代表旧行为时，使用该版本。

通过配置的控制适配器：

1. 启动基线应用。
2. 确认应用和环境正确。
3. 通过真实 UI 操作执行报告路径。
4. 观察到能区分该问题的症状。
5. 重置后重复。
6. 采集基线录屏、截图和状态检查。

如果症状没有在基线上出现两次，就没有有效基线。不要宣称修复有效。

<a id="measure-the-patched-build"></a>
## 测量打补丁的构建

使用相同环境和数据，构建并运行该拉取请求或修复提交。

1. 执行相同 UI 路径。
2. 重复两次。
3. 确认错误状态消失。
4. 确认预期状态出现。
5. 采集修复后的录屏、截图及相同状态检查。

不要止步于编译或测试。修复后的结果必须来自正在运行的打补丁应用。

<a id="outcomes"></a>
## 结果

<a id="confirmed"></a>
### 已确认

基线复现两次，打补丁的构建也解决两次。

- 将运维状态标为已验证。
- 链接该产物。
- 来源预检后，在来源线程发布一条简洁回复。
- 包含修复前后结果。
- 不打开拉取请求。

<a id="insufficient-fix"></a>
### 修复不充分

基线构建和打补丁的构建都出现症状。

- 将运维状态标为已复现但未修复。
- 链接该产物，并说明它未解决症状。
- 如果本次运行尚未发布常规已确认复现的来源更新，则发布该更新。
- 不打开竞争拉取请求。

<a id="inconclusive"></a>
### 无法得出结论

基线未复现、打补丁的应用无法运行，或证据没有展示能区分该问题的状态。

- 不要宣称成功。
- 说明哪一半无法测量。
- 将结果保存在运维线程或运行输出中。
- 不要在来源线程发消息，除非有直接问题需要回答。

<a id="cleanup"></a>
## 清理

停止两个构建，按保留政策移除临时配置文件和采集文件，并将仓库恢复到先前状态，不能丢弃用户工作。
