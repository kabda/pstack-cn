<a id="reproduce-and-fix-issues"></a>
# 复现并修复问题

等待来源线程中可信的分诊标记。通过目标应用的真实 UI 复现完全相同的症状。有现有修复时先验证。只有确认复现后，才尝试有明确边界的修复。

加载自动化提供的外部 Benny 配置。如果配置、所需操作、控制适配器或已完成的功能映射缺失，应以关闭方式失败。

<a id="hard-safety-rules"></a>
## 硬性安全规则

- 在开展任何工作前固定来源频道和根线程坐标。
- 绝不在来源频道发布根消息。
- 每次在来源线程发消息前，都预检来源父消息。
- 协调者是唯一的 Slack 发消息者。
- 受委派的分析工作者只读，返回发现或媒体记录。
- 修复阶段的代码工作者只有在可证实其环境排除了 Slack 凭据和所有 Slack 写入操作时才可编辑。否则由协调者编辑。
- 每个子代理提示词必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 以及其他一切 Slack 写入。
- 绝不给子代理 Slack 令牌、发消息指令、供发消息使用的来源坐标或对外报告权限。
- 如果子代理需要 Slack 写入权限才能运行，就不要启动它。
- 工具机器人是证据来源。除非有人明确将修复委派给它们，否则它们不负责修复。
- 能区分该问题的确切症状必须通过真实 UI 交互出现两次。
- 状态检查可以确认观察结果，但绝不能注入或强制制造症状。
- 未确认复现，就不能编写修复。
- 出现现有拉取请求或提交时，将本次运行切换为验证模式。不要在其基础上另行编写改动。
- 使用 `github.com` 拉取请求链接。
- 采集文件、录屏、日志和令牌不得纳入源代码版本控制。
- 对委派分析使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证过程中应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

<a id="1-freeze-source-coordinates"></a>
## 1. 固定来源坐标

在制定工作列表或委派之前：

1. 要求触发频道与配置的来源频道一致。
2. 如果存在 `trigger.thread_ts`，将其赋给 `SOURCE_THREAD_TS`；否则使用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 将 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 保存为不可变值。
5. 读取来源线程，验证其根消息具有完全相同的坐标。
6. 获取来源永久链接。

绝不用回复时间戳、运维时间戳或状态消息时间戳替换这些值。

每次在来源频道发消息前：

1. 使用不可变坐标读取线程。
2. 确认父消息存在、未删除，且仍属于来源频道。
3. 只能以 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再次读取线程，验证新消息是回复。

任何检查失败，都不发消息。绝不在根层级或后备频道重试。

<a id="2-wait-for-the-triage-contract"></a>
## 2. 等待分诊契约

在配置的结论等待预算内观察来源线程。等待期间保持安静。

仅在以下条件成立时接受结论：

- 作者与 `slack.triage_identity_user_id` 匹配。
- 它是 `SOURCE_THREAD_TS` 下的回复。
- 它恰好包含一个配置的标记。

公开标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

仅对 `bug` 或 `performance` 继续。记录可选的跟踪系统 URL。对于 `other`、缺少结论、不可信作者、标记冲突或超时，应安静停止。

此标记取代私有机器人身份和自由文本结论匹配。

<a id="3-apply-ownership-and-fix-artifact-gates"></a>
## 3. 检查归属与修复产物门禁

开始工作前立即重读线程。

<a id="someone-is-explicitly-fixing-it"></a>
### 有人明确正在修复

当有人明确认领修复、给出具体实施计划，或要求另一个智能体实现、打补丁、修复或打开拉取请求时，应停止。

不要将以下情况视为修复归属：

- 机器人总结证据。
- 工具查询日志或工单。
- 有人要求机器人诊断、解释、检查或复现。
- 机器人发布原因假设，但未同意实施。

判断所请求的操作，而不是看是否出现机器人。

<a id="a-fix-artifact-already-exists"></a>
### 已存在修复产物

如果开放的拉取请求或已合并提交有合理可能修复该报告，应切换到 `references/verify-existing-fix.md`。

产物可以来自线程、跟踪工单、仓库历史或拉取请求搜索。没有提交或拉取请求的口头声明不算修复产物。

如果有人负责此工作，但尚未产生产物，应停止，不要与其竞速。

<a id="4-open-an-optional-operations-thread"></a>
## 4. 创建可选的运维线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里创建一条根状态消息。这是复现工作流中唯一允许的根消息。

将其坐标存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不与来源坐标混淆。

使用配置的普通 Unicode 状态字符串。状态文本保持简短：

- Reproducing（正在复现）
- Could not reproduce（未能复现）
- Blocked（受阻）
- Reproduced（已复现）
- Verifying existing fix（正在验证现有修复）
- Attempting bounded fix（正在尝试有明确边界的修复）
- Draft pull request opened（已打开草稿拉取请求）
- Fix did not land（修复未交付）

优先使用配置的 Cursor Slack 操作。只有用户已为某项范围很小的缺失能力配置 `BENNY_SLACK_BOT_TOKEN` 时才使用，例如编辑这一条状态消息。绝不将令牌暴露给工作者。

如果未配置运维频道，将详细状态保存在自动化运行输出中。不要以来源频道根消息替代。

<a id="5-load-and-check-the-control-adapter"></a>
## 5. 加载并检查控制适配器

读取 `references/control-adapter.md` 及 `control.feature_map_path` 处已完成的映射，然后调用 `control.skill_name` 指定的技能。

找到与报告用户路径匹配的功能映射章节。在操作应用前先阅读它。如果没有章节覆盖该功能，将运行标为受阻，不要编造路径或选择器。

以下七项能力必须全部具备：

1. 启动配置的目标应用和测试环境。
2. 导航到映射功能，并操作其文档记录的状态。
3. 通过点击、输入、按键、滚动、拖动、调整大小或导航操作真实 UI。
4. 检查状态而不修改它。
5. 采集截图。
6. 开始和停止屏幕录制。
7. 清理进程、会话、配置文件和临时数据。

如果适配器不存在或缺少任何必需能力，将运维状态标为受阻并停止。不要把截图、单元测试、状态修改或阅读源码当成 UI 复现。

<a id="6-study-the-report"></a>
## 6. 研究报告

阅读完整来源线程，以及存在时的跟踪工单。

收集：

- 确切操作路径
- 预期行为
- 实际行为
- 两者分歧处能区分问题的状态
- 频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

检查截图和视频。在有帮助时使用只读并行工作者检查代码历史、测试思路、影响范围和媒体。每个工作者都接收一个范围明确的问题和 Slack 写入禁令。

使用 pstack 的 `how` 技能追踪操作在仓库中的路径。使用 `why` 检查回归历史和防御性代码。提出相互竞争的原因假设，并指出能够区分它们的证据。

<a id="7-reproduce"></a>
## 7. 复现

通过控制适配器启动目标应用。

操作前确认应用、工作区、账号、数据集和功能状态正确。使用稳定的应用标记，不要仅依赖窗口顺序或熟悉的标题。

通过真实 UI 操作走完报告路径。

在宣称已复现前：

1. 说清正确的最终状态。
2. 说清错误的最终状态。
3. 到达两者分歧的位置。
4. 观察到错误状态。
5. 重置足够的状态，使第二次尝试独立。
6. 重复相同路径，再次观察到同一错误状态。
7. 在可能时交叉核验一个真实状态值。

预期中的对话框、加载状态或设置步骤不是缺陷。采集能够区分正确和错误行为的最终状态。

使用配置的复现预算。如果在预算内未复现症状，如实报告 `Could not reproduce`（未能复现）。如果环境无法提供某项必需能力，报告 `Blocked`（受阻）并说明缺失内容。

<a id="8-capture-and-review-evidence"></a>
## 8. 采集并审阅证据

成功复现时：

- 录制直到症状出现的完整路径。
- 采集错误最终状态的截图。
- 保存一条简短记录，包含确切步骤和观察到的状态。
- 将产物保存在配置的临时产物目录中。

让只读媒体审查者回答一个问题：证据是否清楚展示了能区分该问题的错误状态？

如果答案是否定或不确定，就尚未确认复现。采集更好的证据，或使用 `Could not reproduce`。

仅在配置了运维线程时向其发布详细证据。来源更新保持简洁。

<a id="9-report-the-repro-outcome"></a>
## 9. 报告复现结果

先更新运维状态。

对于 `Could not reproduce` 或 `Blocked`，不要在来源线程发消息。结果放在运维线程或运行输出中。

确认复现后，预检来源，并最多主动回复来源线程一次：

- 说明问题已复现。
- 如果有运维证据线程，附上链接。
- 最多包含三条简短发现。
- 如果有跟踪工单，附上链接。
- 默认不 @ 负责人。

只有配置的 Slack 操作能将证据留在同一个来源线程，且组织的保留政策允许时，才能附上证据。

等待配置的异议窗口。如果有人证明设置或解释有误，纠正复现一次。在窗口结束且没有有效异议之前，不得开始修复阶段。

<a id="10-verify-an-existing-fix"></a>
## 10. 验证现有修复

存在修复产物时，遵循 `references/verify-existing-fix.md`。

验证必须展示基线上出现症状，而打补丁的构建上症状消失。两条路径都通过真实 UI 各执行两次。

不要编辑现有修复、添加竞争补丁或打开替代拉取请求。

<a id="11-qualify-a-bounded-fix"></a>
## 11. 判断是否可以进行有限修复

仅当以下条件全部成立时才尝试修复：

- 结果是普通的已确认复现。
- 媒体审阅确认了错误最终状态。
- 没有出现现有修复产物。
- 异议窗口内没有人认领修复。
- 运行时证据指出了根因。
- 预计改动符合配置的修复预算和仓库范围。
- 控制适配器能运行基线构建和打补丁的构建。

任何条件不满足，都应保留复现报告并停止，不打开拉取请求。

通过门禁后，将运维状态更新为 `Attempting bounded fix`。

<a id="12-root-cause-and-implement"></a>
## 12. 确认根因并实施

协调者负责每条 Slack 消息、最终差异审查、提交和拉取请求。

只读工作者可以：

- 追踪代码和历史
- 提出测试
- 梳理影响范围
- 审查差异
- 审阅媒体

它们不编辑、不进行外部写入、不发布状态，也不负责修复。

在此阶段，只有工具隔离已将 Slack 凭据和所有 Slack 写入操作从工作者中移除时，才可委派范围严格限定的代码编辑。其提示词仍必须包含明确的 Slack 写入禁令。协调者审查编辑结果，并运行或验证所需测试。如果工具隔离情况不确定，由协调者编辑。

用运行时证据确认机制。编辑前排除竞争假设。

用有依据的最小改动修复根因。

- 有低成本的本地测试目标时，调用 pstack 的 `tdd` 技能，先写失败测试，再修复。
- 如果路径成本高、不明确或大量依赖集成，说明跳过 TDD 的原因。
- 不做无关清理。
- 如果改动超出配置的投入或风险预算，应停止。

<a id="13-prove-the-fix"></a>
## 13. 证明修复有效

保留原始基线证据。

在打补丁的构建上：

1. 执行相同的真实 UI 路径。
2. 重复两次。
3. 展示错误状态已经消失。
4. 展示取而代之的预期状态。
5. 采集修复后的录屏和截图。
6. 交叉核验基线使用的同一个真实状态值。

编译、单元测试、代码审查或看似合理的差异，都不是修复后的证据。

运行聚焦测试，再对改动行为周边的影响范围做冒烟测试。覆盖改动可能影响的相邻状态、输入、权限、平台和失败路径。如果仍有回归，应停止，不打开拉取请求。

<a id="14-open-a-draft-pull-request"></a>
## 14. 打开草稿拉取请求

只有前后对照证据充分后，才进行以下操作：

- 审查最终差异，检查无关改动和秘密信息。
- 运行仓库要求的检查。
- 仓库工作流允许时，创建小型、有序的提交。
- 打开草稿拉取请求。绝不在此工作流中合并或部署。
- 使用跟踪系统支持的拉取请求语法链接配置的跟踪工单。
- 使用配置的公开 URL 格式，通常为 `https://github.com/{owner}/{repo}/pull/{number}`。
- 包含复现步骤、根因、测试结果、修复前后证据和影响范围检查。
- 使用 pstack 的 `unslop` 技能处理拉取请求文本及所有 Slack 更新。

如果创建拉取请求失败，不要宣称成功。在运行输出中保留提交或分支状态，并将运维状态标为 `Fix did not land`。

成功后，将运维状态标为 `Draft pull request opened`，并在运维线程中发布一条带有拉取请求链接的简洁回复。不要再创建来源频道根消息，也不要再次主动回复来源线程。

<a id="15-follow-ups-and-cleanup"></a>
## 15. 跟进与清理

在一个跟进窗口内观察配置的运维线程。

- 根据已收集的证据回答直接问题。
- 当一项具体纠正使设置失效时，应用该纠正，并重新复现一次。
- 不参与人工协调和旁支闲聊。
- 被要求停止时就停止。

始终调用控制适配器的清理能力。产物保留时间不得超过配置的保留政策允许的时长。
