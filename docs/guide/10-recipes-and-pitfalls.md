# 实用配方与常见陷阱

先列出值得复制的提示词，再列出每个人都会犯一次的错误。替换成自己的路径和完成条件即可。这些配方刻意采用口语，因为实际就是这样输入的，技能也能准确理解意图。

![她品尝做好的菜，机器人按配方盒中的食谱烹饪，台面上方钉着 /how、/tdd 和 /loop 卡片。](./images/recipes.jpg)

<a id="understand-an-unfamiliar-subsystem"></a>

## 理解陌生子系统

```text
先用 /how 理解这个初始化如何工作，再用 /why 弄清它最近为何出错。
```

先机制，后历史。每项技能的报告会说明搜索过哪些来源，让你知道答案的依据。

<a id="restate-a-noisy-report-before-touching-code"></a>

## 接触代码前先复述冗杂报告

```text
/poteto-mode 阅读这个讨论串。用自己的话，以通俗英语复述根本问题。暂时不要修改任何代码。
```

误读会在复述中暴露，纠正只需一条消息。在智能体陈述自己的理解前，先保留你的原因猜测。`/in-your-own-words` 只要求复述，不运行操作手册。

<a id="sharpen-a-prompt-before-you-send-it"></a>

## 发送前打磨提示词

```text
/sharpen 为新的计费服务编写入门文档。
```

智能体会指出专家还会做哪些你没要求的事、会从什么原始材料开始、使用什么方法和工具，以及什么外部检查能证明结果正确。它会据此改写提示词并返回，不执行任务。改写读起来合适时再发送。

<a id="prototype-before-you-pick"></a>

## 选择前先做原型

```text
/poteto-mode 为设置布局做几个原型方案。放在一个切换器后面，并发给我每个方案的截图。
```

你根据可运行的东西选择，而不是描述。智能体在过程中自行回答布局和耗时问题。

<a id="turn-a-settled-design-into-a-plan"></a>

## 把确定的设计转为计划

```text
/poteto-mode 把这个设计变成计划。拆成小而可验证的 PR，每个都有自己的证明。
```

等设计确定后再要求。计划本身是交付物，也会指出负责执行的操作手册。

<a id="get-a-second-opinion-on-a-design"></a>

## 为设计获取第二意见

```text
请 /arena 对这个讨论串和我们的做法提供第二意见
```

当前设计成为多个候选方案之一，综合结果会告诉你，小组找到更好的方案，还是确认已有方案。与回退设计的高成本相比，这点开销很小。

<a id="check-independent-slices-in-parallel"></a>

## 并行检查独立切片

```text
/swarm 用各自的 check.sh 检查 packages/ 下每个包。每个包一个工作代理。汇成一份报告。
```

每个工作代理负责一个包。父代理等待所有切片，返回一份 `PASS`、`ISSUES` 或 `BLOCKED` 报告，而非原始工作代理输出堆积。

<a id="review-a-branch-skeptically"></a>

## 审慎审查分支

```text
/interrogate 审查整个分支，保持怀疑。暂时不要修改任何内容。除非确实是缺陷或行为回归，否则不要挑细枝末节。
```

限定语有实际作用。“暂时不要修改任何内容”保持只读，避免琐碎挑剔的规则则预先过滤噪声，让验证后的发现值得花时间。

<a id="fix-a-bug-through-a-failing-test"></a>

## 通过失败测试修复缺陷

```text
/poteto-mode 先复现重复写入。如果有低成本测试路径，就用 /tdd。然后修复并重新运行。
```

“如果有低成本测试路径”很重要。通过脆弱 mock 强行做测试，比运行真实命令证明得更少；操作手册允许明确指出这一点。

<a id="repro-and-fix-a-report-with-proof"></a>

## 带证明地复现并修复报告

```text
/poteto-mode 用 /verify-<app> 复现。如果 main 上能复现，就修复并给我看证明视频。
```

“如果 main 上能复现”允许在缺陷已消失时提前结束。视频让你在阅读差异前就能检查修复。

<a id="prove-a-property-tests-rarely-reach"></a>

## 证明测试很少覆盖的性质

```text
/create-formal-verification-skill 重试队列。一条消息绝不能投递两次。
```

你会得到一项在明确范围内所有情况都被检查的性质；如果代码已经违背它，会得到以代码术语表述的反例；还会得到项目技能，供下一个智能体在改动相关代码时运行。

<a id="vet-a-number-before-you-post-it"></a>

## 发布数字前先审核

```text
/benchmark-checklist 在把这项 40% 加速写进 pr 描述前，先审核它
```

你会得到更快、更慢、无可测差异或无法得出结论的判断，以及运行次数、范围和限制因素。

<a id="stop-correcting-the-same-mistake"></a>

## 不再重复纠正同一错误

```text
/correct 智能体总是添加新配置标志，却不在 schema 中注册
```

修复以架构、类型、lint 或测试的形式落在仓库中，让下一个智能体无法再犯。

<a id="ask-how-without-starting-the-work"></a>

## 只问方法，不启动工作

```text
/poteto-help 如何让 poteto-mode 在每轮对话中都保持启用？
```

你会得到答案、一条可发送的提示词及来源链接。发送提示词前不会执行任何工作。

<a id="keep-a-run-honest-while-youre-away"></a>

## 离开时保持运行可信

```text
我要睡觉了，持续自主推进，直到所有测试夹具通过。不要停止。保留早晨可审计的决策日志。
```

完整约定见[通宵运行页面](./07-overnight.md)。当任务和完成条件已经在对话中时，简短形式就有效。

<a id="redirect-a-drifting-run"></a>

## 纠正偏离方向的运行

引导提示只需一行：

```text
我说的目标是复现，还没有要求修复。
```

```text
应用“证明它能工作”。展示真实输出，而不是构建日志。
```

```text
/unslop 清理那段文字，不要用长破折号
```

通常不需要更多话，只需要正确的名称。[原则页面](./08-principles.md)就是词汇表。

<a id="get-the-reply-in-plain-words"></a>

## 用通俗语言回复

```text
/bro
```

这就是完整提示词。[`/bro`](../../skills/bro/SKILL.md)像人与人交谈一样，简短、不用行话地重述上一条消息。回复在技术上很详尽，但你仍不明白它说什么时，就用它。

<a id="catch-up-on-a-chat-you-left-running"></a>

## 跟上仍在运行的聊天

```text
/ketchup
```

[`/ketchup`](../../skills/ketchup/SKILL.md)用通俗语言说明自你上一条消息以来的变化，然后列出等待你决定的事项，并附推荐、证据和风险。报告时不作任何改动。

如果想观看回顾，可以运行 [`/ketchup-video`](../../skills/ketchup-video/SKILL.md)。它会用带字幕的简短幻灯视频展示过程，并在下方用文字列出等待你决定的事项。

<a id="the-pitfalls"></a>

## 常见陷阱

- **在提示词中罗列技能。** “先 /how，再 /architect，然后 /arena”会打乱操作手册已有的步骤顺序。说明目标和约束；只有要覆盖默认选择时才指定技能。
- **完成条件模糊。** “改好一点”没给 `/loop` 任何可检查内容。提供能通过或失败的命令或产物。
- **先说原因猜测。** 智能体会搜索你指向的地方。先让它复述问题，再分享直觉。
- **接受第一个设计。** 一次尝试会固定模型最先想到的形态。要求原型或 `/architect`，根据证据选择。
- **打磨抽象计划。** 对没有代码支撑的计划做对抗审查，会虚构永远不会发生的风险。先用原型解决未决问题，再审查实际产物。
- **并行智能体共用一个工作树。** 它们会相互覆盖，而且没人能说清是谁改了什么。使用云端智能体，或明确“每次尝试各用一个工作树”。
- **尚未信任循环就开始循环。** 无法验证自身工作的循环，只会更快地产生未经检查的工作。先让验证技能正常工作。
- **相信未经审核的数字。** 热缓存或被跳过的代码路径能伪造加速。数字用于任何地方前，先运行 `/benchmark-checklist`。
- **手动反复纠正同一错误。** 聊天中的纠正只帮助一次运行。`/correct` 修复仓库，防止后续运行重犯。
- **用 `/arena` 做覆盖。** `/arena` 重复同一设计或代码任务说明，再选基底并融合最佳部分。`/swarm` 划分切片或已声明竞赛组，汇成一份报告。
- **接受每条审查评论。** 机器人与人类都会把真实发现和噪声放在同一列表。`/interrogate` 只保留重跑能证明的发现，并列出放弃内容及理由；两种判断你都可以推翻。
- **把 `auto` 当作模型 slug。** `auto` 和 `inherit-parent` 都表示“省略 model 字段，让子代理继承父聊天模型”。[设置](./01-setup.md)介绍了角色。
- **因构建变绿就报告成功。** 构建只能证明可以编译。要求真实命令、流程、存储值或性能剖析，并期待回复附带证据。
- **徒手写 `SKILL.md`。** 通过[编写或修改技能操作手册](../../skills/poteto-mode/playbooks/authoring-a-skill.md)，确保进行验证与审查。
