# 验证结果并创建 PR

“能编译”不是证据。[证明它能工作原则](../../skills/principle-prove-it-works/SKILL.md)要求智能体在报告成功前检查真实产物，而你的任务是让“真实产物”可以被检查。本页涵盖：明确完成条件、审核测量数字、为应用生成验证技能、形式化验证测试很少覆盖的性质、创建 PR，以及推进至合并。

验证是大多数智能体工作中最慢的一步，因为它通常在等人。让智能体有能力完成验证，你就不再是瓶颈。跳过它，运行更多智能体也只会带来更多未经检查、等待你审查的工作。

![原型飞机飞过真实测试航线，一位女士用秒表计时，机器人录像并检查清单；终端显示验证通过、证据已捕获。](./images/verification.jpg)

<a id="state-the-finish-condition-up-front"></a>

## 预先说明完成条件

在第一条提示词里，用合适的话说明什么算完成：

```text
/poteto-mode 为这条命令增加 json 输出。文本输出必须逐字节不变，json 可以解析，两者都要针对示例项目运行。向我展示证据。
```

现在智能体拥有三项可运行的检查，而不只是一个需要满足的感觉。回复应包含精确命令及输出。如果某项检查无法运行，合格回复会明确说“无法得出结论”。没有证据却自信满满的回复是警讯。

检查应与改动对应：

- CLI 改动运行真实命令。
- UI 改动在运行中的应用内走一遍改动流程。需要与参考逐像素一致时，[视觉一致性操作手册](../../skills/poteto-mode/playbooks/visual-parity.md)会将截图与冻结基线做差异比较，而不是凭肉眼判断。
- 解析器或迁移重放保存的输入。
- 性能改动比较前后的性能剖析。
- 存储改动读回写入的值。

要求以可亲自检查的产物提供证明：先失败后通过的测试、前后视频、跟踪记录、截图。如果修复已合并，要求在 main 上再次运行同样检查。产物胜过听起来合理的解释，因为你无需重放整个过程就能质疑它。

对于你不完全放心的小差异，[`/blast-radius`](../../skills/blast-radius/SKILL.md)会寻找它可能在别处破坏什么。它会找到确保改动安全的关键事实，并通过运行代码证明，而不是靠论述。

<a id="vet-a-measured-number-with-benchmark-checklist"></a>

## 用 `/benchmark-checklist` 审核测量数字

前后对比数字最容易无意中出错。热缓存、一侧使用调试构建，或计时区间内根本没执行工作，都能产生看似可信的加速。在报告数字或据此行动前，输入：

```text
/benchmark-checklist 在把导出加速写入 pr 前，先审核它
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)提出七个问题，每个都要求运行证据：

1. 是什么限制了这个数字，为什么不是它的两倍？
2. 各方是否都采用了与生产一致的调优方式？
3. 结果是否突破了磁盘带宽或核心数等物理限制？
4. 是否有任何错误或错误输出？
5. 交替运行能否复现，是否有中位数和范围？
6. 在用户等待的端到端路径上，这个变化有意义吗？
7. 工作是否确实发生在计时区间内？

结论会是更快、更慢、无可测差异或无法得出结论，并附运行次数、范围和限制因素。无法说明限制因素，或某一方未调优时，它会判为无法得出结论。`/poteto-mode` 已经在性能问题和爬坡优化操作手册内运行此清单，因此当你在这些流程之外做测量，或他人的数字好得令人怀疑时，再自行输入。它是[解释数字原则](../../skills/principle-explain-the-number/SKILL.md)的实际执行形式。

<a id="create-a-project-verification-skill"></a>

## 创建项目验证技能

上方关于 UI 的条目隐藏着一个真实要求：智能体需要可脚本化操作应用的方法。项目已有就很好；没有则运行：

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)会向仓库取证，而不是采访你。它会查清用户会接触什么、如何本地启动应用、什么能驱动它（优先已有运行环境，否则采用浏览器和 CDP、PTY，或普通 HTTP）、什么证据能证明行为，以及两个实例能否并行运行。只有代码无法回答的问题才会问你。

它写入 `.cursor/skills/verify-<app>/`，其中面向智能体的指令具有精确命名的 Launch（启动）、Doctor（诊断）、Drive（操作）、Evidence（证据）和 Cleanup（清理）部分；随附脚本时还包含 Helpers（辅助工具）部分。此外，在 `features/` 下建立功能图，索引应用的功能及每项功能有效的证明结果。技能提供一份[完整功能图示例](../../skills/create-verification-skill/references/feature-map-example/)，包含 README 索引和每个功能一个文件，各文件使用四个必需的 H2 标题。交付前，生成器会端到端证明技能一次：启动、诊断检查、操作一个功能、捕获证据、清理，再确认证据在清理后仍保留。如果证明失败，就不要使用生成结果。

此后，在这个仓库中，“在应用内验证”就成为任何智能体都能执行的步骤，无需再对话设置。想要特定形式的证明时，在提示词中指定它：

```text
/poteto-mode 构建批量归档操作。用 /verify-<app> 验证改动，并展示视频和截图作为证明。
```

```text
/poteto-mode 用 /verify-<app> 复现。如果 main 上能复现，就修复并给我看证明视频。
```

验证技能正常工作后，[`/swarm`](../../skills/swarm/SKILL.md)可按功能图条目拆分完整检查并汇总结果。一组验证代理也能用足够大的样本确认性能收益，或在 PR 交付前对应用做模糊测试以发现回归。

把验证技能当作基础设施，而非一次性产物。提交它，让团队每个人、每个智能体都以同样方式操作应用。然后[构建杠杆工具](../../skills/principle-build-the-lever/SKILL.md)。当智能体不断编写一次性点击脚本时，要求提供一个小型控制 CLI，让技能改为调用它。智能体消耗的 token 会更少，每次运行也会变得可重复。适合智能体使用的 CLI 有以下特点：

- 少量可组合、各自完成实际工作的命令，而非大量功能单薄的命令。
- 破坏性操作提供 `--dry-run` 选项。
- 子命令逐步揭示功能，而不是一次全部展示。
- 错误消息说明下一步该做什么。
- 详细的 `--help` 文本。
- JSON 等机器可读输出。

同时也让开发环境可重复：预置数据、测试用户，以及一条每次都以相同方式启动环境的命令。

<a id="keep-the-verification-skill-honest"></a>

## 保持验证技能可信

应用会变化，功能图会过时。至少每天运行一次，最好通过定时自动化，免去人工记忆：

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)审核生成的技能：先为每项功能并行派出一个只读源码阅读代理，再进行一轮实际操作，覆盖所有已映射功能。最终只有三种结果之一：`clean` 表示完全覆盖且无内容需交付；`changed` 表示一份包含已证明修正的 PR，改动仅限验证技能自身目录；`blocked` 则指出阻塞因素。它绝不修改产品代码。如果实际操作发现产品回归，它会报告回归，而不是通过修改文档掩盖问题。

<a id="prove-a-property-with-a-formal-verification-skill"></a>

## 用形式化验证技能证明性质

验证技能证明你实际操作过的路径。有些缺陷藏在没人走过的路径：两次重试重叠、锁在写入中途到期、状态变化乱序到达。测试很少触及这些情况。对于此类缺陷代价高的代码，运行：

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)从代码中选择目标：代码作出的一项承诺，违背时会伤害用户，而测试很少覆盖这种情况。它选择价值最高的目标，而非最容易验证的目标。也可以指定区域或缺陷，从那里开始：

```text
/create-formal-verification-skill 作业租约和重试逻辑。同一作业绝不能同时运行两次。
```

问题决定工具。事件是否可能以错误顺序发生，适合对设计的小型模型使用模型检查器；无论代码是什么语言，TLA+ 都是默认选择。代码对所有输入是否正确，适合直接作用于代码的验证器。如果没有适用于该语言的验证器，智能体会说明，并用生成的输入测试真实代码，而不是手写一个函数模型。必须在任意规模都成立的性质，可能需要证明。智能体会说明所选工具及理由。

它验证一项性质，并展示该性质在有缺陷的代码变体上失败，因为从没见过失败的检查证明不了什么。如果当前代码已经违背该性质，你会得到用代码术语表述的一小段反例步骤。性质保持原样，因此发现仍是发现。除非你要求，否则产品代码不变。

它写入项目内技能，告诉下一个智能体：改动是否触及被验证代码、如何用一条命令运行检查，以及如何区分真实缺陷与建模错误。交付前，生成器会对一项破坏该性质的临时改动执行一次此技能，检查必须抓到它。交接内容说明验证了什么、用了什么工具和边界、检查发现了什么，以及不覆盖什么。通过只覆盖模型或边界，不代表整个系统。

技能还会记录每项检查覆盖哪些代码，以及检查最后一次与代码一致时的 commit。跳过技能的合并和重构，可能让检查对已经不存在的代码描述继续通过。之后应运行 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)。它根据代码更新验证，重新运行，展示每项更新后的检查仍能失败，并说明每次失败是验证漂移还是代码缺陷。

<a id="show-the-behavior-as-a-statechart"></a>

## 用状态图展示行为

模型术语中的反例能够说服你，但负责行为的 PM 或设计师需要用自己的术语看懂它。运行：

```text
/statechart 用户离线编辑笔记时看到的内容
```

[`/statechart`](../../skills/statechart/SKILL.md)从 TLA+ 模型生成展示用户所见内容的 Mermaid 状态图，让图和已检查模型无法相互漂移。读者的规则（“离线时绝不会看到 Synced”，即“已同步”）成为不变量。图会标记每个违背规则的状态，报告则用读者的语言给出到达它的最短路径。交接前，智能体会在真实代码中复现每条缺陷路径，防止把建模错误当作缺陷交给读者。

<a id="open-the-pr"></a>

## 创建 PR

```text
/poteto-mode 创建 pr。提交要小且顺序清楚，描述中包含证据。
```

[创建 PR 操作手册](../../skills/poteto-mode/playbooks/opening-a-pr.md)在工作树中操作，将工作变基为小而有序的提交，清理差异、润色文字，并返回 PR 链接。五个聚焦的小 PR 胜过一个庞大 PR；后续堆叠 PR 胜过不断膨胀的分支。

<a id="drive-the-pr-to-merge-ready-with-babysit"></a>

## 用 Babysit 推进 PR 至可合并

PR 一创建就开始累积阻塞：检查失败、审查者评论、主干推进。把这些反复变化交给 [Babysit 操作手册](../../skills/poteto-mode/playbooks/babysit.md)：

```text
/poteto-mode babysit 这个 pr，让它全部变绿。
```

Babysit 会监视 PR：GitHub 上使用随附监视器，Origin CLI 可用时则使用它。按顺序处理阻塞：先冲突，再审查讨论，最后 CI。所有已知修复合并为一次推送，让检查只重启一次，而不是每次修复后重启。评论分流保持审慎，因为人类和机器人会把真实问题与噪声混在同一列表中。真实发现会得到修复；噪声则会被驳回，并将反证发布到讨论串。若只想知道状态，可以缩小请求，Babysit 会回答而不启动循环：

```text
/poteto-mode 看看 pr 123 的状态。还有什么未解决？
```

Babysit 在可合并时停止。即使全部变绿也绝不合并，因为合并是另一项决策。

<a id="land-the-stack-with-shipping"></a>

## 用 Shipping 合并堆叠

变绿不等于安全。准备落地时，请明确说：

```text
/poteto-mode 合并这个堆叠。
```

[Shipping 操作手册](../../skills/poteto-mode/playbooks/shipping.md)在启用任何操作前，独立验证每个 PR。每个 PR 都由一个新的智能体实际证明行为，判断改动的智能体绝不会是编写它的那个。然后 Shipping 只从底部合并连续通过验证的部分，每次一个 PR，默认通过 GitHub，Origin CLI 可用时使用它，并报告第一个中断链条的 PR。位于未验证 PR 上方的已验证 PR 必须等待，因为合并它会把下方未验证的缺口也带进来。
