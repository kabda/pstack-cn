# 修改代码前先理解它

修改不理解的代码，会让隐蔽的回归进入交付；对智能体和你都一样。智能体通常以两种方式失败：误读你的意图，或缺少把工作做对所需的上下文。[提示词应包含什么](./02-poteto-mode.md#what-goes-in-a-prompt)处理前者，本页处理后者。

pstack 提供四种入口。`/how` 解释代码当前做什么；`/why` 挖掘它为何形成现在的结构；`/teach` 把两者融合为一份讲解；`/recall` 重建你最近在某个主题上的上下文。每一项也都会要求智能体用你能核对的语言解释自己。这就是监督一个可能比你更熟悉代码的智能体的方法。

![一位侦探用放大镜研究机器蓝图，机器人在旁取来案卷；她身后的证据板在 /how 和 /why 下连接各条线索。](./images/understanding.jpg)

<a id="start-with-a-read-only-investigation"></a>

## 从只读调查开始

原因不明时，要求提供发现，而非直接修复：

```text
/poteto-mode 调查为什么后台作业每隔几小时就超时。告诉我已知事实、使用了哪些数据，以及最有可能的假设。暂时不要修改任何代码。
```

“暂时不要修改任何代码”会把任务路由到[调查操作手册](../../skills/poteto-mode/playbooks/investigation.md)。它运行 `/how`，对于动机相关问题加用 `/why`，并返回有来源引用的解释。需要在选项中作选择时，会给出建议和利弊对照表。询问“使用了哪些数据”，能让智能体区分证据与猜测。发现指向某个修复方案后，再以新任务启动修复。

<a id="trace-behavior-with-how"></a>

## 用 `/how` 追踪行为

```text
/how 我们如何对通知去重？查询订阅者时是否存在 n+1 问题？
```

直接提出你的真实问题。[`/how`](../../skills/how/SKILL.md) 会阅读代码，像资深工程师带你熟悉子系统一样，解释运行流程、关键类型和不明显的细节。面对大型子系统，它会先并行派出二到四个只读探索代理；对于范围窄的问题，则直接阅读并解释。

<a id="dig-up-history-with-why"></a>

## 用 `/why` 挖掘历史

```text
/why 重试上限为什么设为五次？当时的理由现在仍成立吗？
```

[`/why`](../../skills/why/SKILL.md) 从版本控制出发，然后并行查询 MCP 暴露的各种证据类别，例如问题跟踪器、长篇文档、团队聊天、可观测性、错误跟踪和分析。报告会为所有内容提供来源，区分直接证据与推断，记录不足时会使用“似乎”等措辞。没有找到结果也会报告，因为“没有人记录原因”本身就是一种答案。

两者可以自然组合。如果怀疑历史能解释眼前的混乱，`do why first then how`（先运行 why，再运行 how）是一条好提示词。

<a id="actually-understand-it-with-teach"></a>

## 用 `/teach` 真正理解

```text
/teach 向我解释这个 PR 如何改变重试。说服我它解决的是原因，而非症状。
```

当摘要不够用时，可以使用 [`/teach`](../../skills/teach/SKILL.md)。它会运行 `/how` 和 `/why`；对于小改动，可能只运行其中一个，然后把发现编织成通俗讲解，通过一幅接一幅的图示逐步展开。“说服我”这种提法值得复用：它让讲解成为可检验的论证，而不只是导览。

它也适用于智能体自己的选择：

```text
/teach 向我解释为什么采用这种实现，而不是队列。你做了哪些取舍，为什么？
```

教学对智能体与你同样有益。必须解释工作的智能体，就必须阅读代码，用证据支撑每个说法，而不是自信地宣告后就继续。

<a id="rebuild-your-own-context-with-recall"></a>

## 用 `/recall` 重建自己的上下文

```text
/recall 帮我回顾上周的导出工作
```

[`/recall`](../../skills/recall/SKILL.md) 会检索你自己的近期聊天及共享记录（问题、此前修复、仍在触发的错误），简要说明现状和下一步。旧聊天中有新智能体缺少的上下文，因此在旧主题上开始新工作时，先加载它，再提供新输入：

```text
/recall 回顾我昨天在虚拟化列表上的工作，然后阅读这份缺陷报告。
```

如果想恢复某个特定聊天，应使用下方的会话接续操作手册，而不是 `/recall`。

<a id="take-over-prior-work-with-session-pickup"></a>

## 用会话接续接手既有工作

当另一个智能体（或上周的你）留下一个未完成的分支时：

```text
/poteto-mode 接手这个分支。阅读决策日志，弄清哪些已经完成，并从那里继续。不要重做已完成的工作。
```

[会话接续操作手册](../../skills/poteto-mode/playbooks/session-pickup.md)把已有记录视为权威依据。它会重建分支状态和决策，指出恢复点，并根据原始目标验证继承而来的说法，而不是从头重新推导一切。

**陷阱：** 不要因为“智能体反正会读代码”而跳过本页技能。没有先追踪并建立模型就开始编辑的智能体，往往会在第一个貌似合理的位置修补症状。先运行 `/how` 比再引入一个缺陷便宜。
